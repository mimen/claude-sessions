CCS · Implementation plan

Summaries you can act on

Enrichment works — 468 of 469 top-level sessions carry a generated description. But each one is a chronicle rather than a status: it narrates the session in the order things happened, in the passive, hedged register a model reaches for by default; it states the same fact three times across three fields; and it asserts that work is live without ever checking whether it landed. v40 changes what the model is asked for, gives it evidence about the world, and adds the two surfaces that turn 468 descriptions into a queue.

2 · What the store says about itself

Every claim below is a query against the live catalogue, not an impression. They are the reason the changes in section 3 are the changes and not some other set.

The recommendation doesn't discriminate

continue is 219 of 468 verdicts. A field that says yes to half the store sorts nothing. The cause is structural: enrichment reads only the transcript, and a transcript that stops mid-sentence is what every abandoned session looks like. So continue does not mean "live work worth resuming" — it means "this didn't end tidily."

Checking those 219 against the world they describe: 79 ran on a feature branch, the population where the question has a checkable answer. The other 140 were on master or main, where "is the branch merged" is trivially true and says nothing.

The clearest single case: the constellation-edges session recommends continue with "Finish CLI implementation, run tests/typechecks, verify the brief, commit to a branch, write the child report, and notify the loop-manager parent." That work is 5eb1d5b feat(catalogue): constellation edges — parent + skill per session, merged into master. The panel is telling you to go finish something that shipped.

Three fields carry one fact

In the row in section 1, the summary's closing clause, the whole of outstanding, and the whole of reason assert the same thing: the trial launch was interrupted. That is the parsing tax — three paragraphs read, one state extracted. reason averages 132 characters and appears on all 468 rows, but on the 401 where the verdict is continue or complete it only restates the verdict in hedged prose.

outstanding is a list pretending to be a sentence

199 of the 371 non-empty values chain multiple actions with commas. The longest: 

User must review/approve the proposed drive access model; then apply
permissions, finish UI-only drive renames/deletion of six empty drives,
and resolve Charles Louis's profile location and Johann Sevilla's
current reduced-status conflict.

Four actions and two people, 232 characters, one sentence.

The cwd verdict is unverifiable noise

Enrichment judges whether a session's working directory suits the work it did, and is meant to answer with a key from a curated registry of launch locations so the answer can be checked. It may fall back to a free-text absolute path only when no registered location fits — the escape hatch, which exists because that case is itself a signal that a location should be registered. 155 of 468 sessions (33%) are flagged as running in the wrong directory, and every one of those took the escape hatch, because ~/.ccs/locations.toml was never installed on this machine — it ships with the unmerged /ccs:new router. The suggestions include /Users/mimen/claude-sessions, which does not exist, and a bare /Users/mimen. Each prints a warning-coloured line in the dossier.

The gap nothing surfaces

enrichment-schema.ts states the design intent plainly: enrichment is observed state, lifecycle is stored intent, and the gap between them is the signal. The gap is currently 162 sessions wide — recommended complete, never marked — and no command presents it.

3 · The twelve decisions

Split summary into state and history

The defect is ordering, not length: every summary opens with what the session set out to do and buries where it landed. Two columns make the separation structural, so a reader cannot be forced to parse a chronicle to find a state. The dossier leads with state alone and reveals history on demand.

Rejected: rewriting the schema descriptions only. Cheaper and reversible, and the precedent was good — v39's 33%→93% first-pass jump came from exactly that kind of edit. But an instruction to "lead with the state" is a request the model can drift from, whereas two columns cannot be run together. Since the cutover requires a full re-enrich either way, the migration was nearly free.

Split outstanding into next and remaining

next is the single immediate action, imperative, ≤120 characters. remaining is everything else, optional, ≤250, rendered dimmer. Keeping both as scalar TEXT rather than a list has a second payoff: SELECT next FROM catalogue WHERE recommendation='continue' is a to-do list across the whole store, which is what makes ccs next a one-line query instead of a parse.

Rejected: a JSON array of 1–3 bullets. More faithful to data that is genuinely a list, and the forced tool call would return a native string[]. But the original design explicitly refused JSON blobs for enrichment on the grounds that this is state which wants to be queried and sorted, and that reasoning still holds.

reason becomes conditional, enforced at parse time

Required when the recommendation is archive or handoff, or when junk is true; required to be empty otherwise. The rule is deterministic and checked in validateEnrichment, rather than an instruction to "mention it when interesting" that a model interprets loosely. This removes roughly 401 dead lines and keeps the ~67 that justify a call you would otherwise distrust. 

const needsReason = rec === "archive" || rec === "handoff" || junk;
if (needsReason && !reason) return "archive/handoff/junk requires a reason";
if (!needsReason && reason) return "reason is only for archive/handoff/junk";

Rejected: dropping the column. The world block will make archive verdicts both more common and more surprising, and an unexplained "archive this 200-message session" is exactly the prompt to open the transcript — the trip the panel exists to save.

junk gains a coherence rule and a bulk lane

junk=true now forces recommendation='archive'. Today 17 junk rows recommend complete — a PONG probe technically succeeded, but "complete" is the wrong shelf for it, and left alone it files "Unavailable fake todo tool probe" into your success history. The 28 still-idle junk sessions then appear in ccs triage as one collapsed group with a single archive-all key. The population is safe to treat in bulk: the largest is 16 messages and none contain work.

Rejected: auto-archiving junk in the sweep. Defensible on the evidence and it would clear all 28 with no keypresses, but it makes a model verdict write a lifecycle change, which the original design refused on principle and which contradicts the read-only stance taken for triage below. Also rejected: deleting the boolean and letting archive carry it — that collapses "never worth starting" and "a real attempt that failed" into one undifferentiated pile.

The cwd question is registry-gated

When ~/.ccs/locations.toml is absent, the <locations> block and the three cwd properties are dropped from the JSON Schema for that call entirely. A model that is never asked a question it cannot answer well cannot invent an answer. The columns stay in v40, dormant, and the feature switches itself back on the day the registry lands — no code change needed.

Rejected: blocking on the registry. Extracting locations.toml from feat/ccs-new-router fixes the root cause, but that branch belongs to another session, so it would make v40 wait on a merge this thread does not control. Also rejected: deleting the cwd fields. They catch a real habit; the problem is the missing registry, not the question.

The premise was already stale · 2026-07-26

The registry is installed. ~/.ccs/locations.toml is a symlink to ClaudeConfig/session-routing/locations.toml carrying 31 curated locations, and the router work it ships with merged (docs/ccs-new-router-shipped). The 155 free-text verdicts were all generated before it landed.

So the gate is inert on this machine, which is exactly the designed outcome — "it switches itself on the day the registry lands" — and it stays as the guard for any machine the registry has not reached. The cwd question is live again, and the first swept sessions returned real keys (repos, assistant) with free text used only where it is genuine signal: /Users/mimen/Programming/Repos/imsg is a real directory that is not yet registered, which is the escape hatch doing its job rather than inventing a path.

The copy register is dry operator, second person

Present tense, direct address, plain verbs, no hedges, and metrics only when the number changes what you would do. "The user" is absurd in your own catalogue. In the section 1 example this halves the character count, and the cut falls entirely on decoration — test counts, percentages, and adjectives like "upstream-friendly" — rather than on substance.

Rejected: keeping the impersonal analyst voice. It never misattributes to you an action a delegated subagent took, which is a real edge. But it is also the register producing "substantially complete" and "the session was tasked with", which is the complaint that started this thread.

A <world> block goes into the prompt

Enrichment currently receives seven things — title, cwd as a string, message count, last activity, the skeleton (the session's opening turns, as stored by the indexer), the transcript tail, and the locations registry — and never touches the world any of them describe. It gains a block of deterministic facts: whether the cwd still exists, the branch's existence and merge state, whether the worktree is present and dirty, and how many later sessions have run in the same directory.

All of it is readable from .git/HEAD, .git/refs/, and packed-refs as plain files, plus one index query — no process spawn, so src/enrich/provenance.test.ts, which fails if any module under src/enrich gains a spawn or harness invocation, keeps passing unchanged.

Corrected during implementation · 2026-07-26

Two of the four git facts above are not obtainable without running git, and the paragraph claiming otherwise was wrong. Merge state is a commit-graph ancestry question: answering it means decompressing commit objects and walking parents, and those objects may sit inside packfiles. Worktree dirtiness is an index-versus-worktree diff, including blob hashing for anything whose stat data moved. Neither is a file read. The measured evidence in section 2 came from running git merge-base --is-ancestor in a shell, which src/enrich is forbidden to do.

Shipped: the readable subset — cwd existence, whether the session's branch still exists (checking both loose refs and packed-refs, since a gc'd branch has no loose file and would otherwise read as deleted), the currently checked-out branch, and the successor-session count. The cost is small and measured: of the 61 stale continue verdicts on feature branches, 54 were "branch deleted" — which is readable — and only 5 were "merged". The block retains roughly 89% of the signal that motivated it.

Open: recovering merge state and dirtiness means allowlisting a git read inside provenance.test.ts. That guard's stated purpose is preventing session-minting harness calls, which git cannot do — but amending a structural safety property is a decision, not an implementation detail, and it is not taken here.

What the model actually receives:

<world>
  working directory: exists
  the branch this session ran on: DELETED since
  branch checked out there now: master
  later sessions in this directory: 14
  most recent of those: 2026-07-24T09:12:00.000Z
</world>

Liveness is also recomputed at render time

This is the decision a stored-only design would have got wrong. Enrichment's freshness rule is driven by progress rather than a clock: a session is re-enriched once it has gained 10 messages, or if it has moved at all and its stored description is more than six hours old. An idle session is therefore enriched once and never again, which is exactly what makes the steady state cost nothing.

But world state changes while a session sits still — you merge the branch, the session gains no messages, and no rule fires. Any world verdict written into a column is therefore guaranteed to rot, silently and confidently. The prompt block keeps the model's verdict honest at write time; the dossier recomputes the banner on open, so the panel is never wrong even on a two-month-old enrichment.

Coverage comes from successor sessions, not git alone

The branch check sounds decisive and covers less than it appears to. Across all 466 enriched sessions with a recorded cwd:

So the world block also carries a count of how many later sessions have run in the same cwd. It is a pure index query — no filesystem, no git, no model — and it works identically for a repo and for the vault. 412 of 466 enriched sessions have at least one successor. It does not prove work landed, but "14 sessions have worked in this directory since" is decisive staleness information.

Rejected: successors only, dropping git. One uniform signal with far better coverage and the simplest implementation, but it gives up the sharpest verdict available — "branch merged, this landed" is qualitatively better than "someone worked here since."

ccs triage — the disagreement queue

A dedicated command listing only sessions where the verdict contradicts the lifecycle, most recent first, one keypress to apply, skip, or open. Batch flow for a batch problem: ~180 items is fifteen minutes of keypresses versus 180 dossier visits that will not happen. Read-only until a key is pressed, so no model verdict mutates anything unattended. A --list --json form feeds a scheduled digest. 

$ ccs triage
  ⚠ enrichment sweep last succeeded 5h ago · 42 failed runs

  ▸ junk · 28 probes and throwaways        [A] archive all  [e] expand

  1/135   a3f12c9d · idle → complete
  T3 static-seam refactor and local trial
  Refactor is green and merged; the branch was deleted 3 weeks ago.
  ⚠ world: branch gone, cwd clean

  [c] complete  [a] archive  [s] skip  [o] open dossier  [q] quit

Rejected: a TUI-only filter. Zero new surface area and it reuses navigation that already exists, but it cannot feed a scheduled digest or a morning brief. Note: ccs inbox was unavailable as a name — it is agent-to-agent identity messaging in src/inbox/, unrelated.

ccs next — the "where was I" list

A read-only projection over sessions whose verdict is continue: id, title, and the next line. Nothing is stored and nothing can be added, so it is recomputed on every run and a row disappears the moment its session is closed out. It answers a question Todoist structurally cannot — Todoist only knows about work you deliberately filed, whereas this is the work you were interrupted in the middle of. 

$ ccs next
  a3f12c9d  T3 static-seam refactor
            Launch the build and try the refactor       · 2d · t3code
  9c02b41f  CCS harness swap and restart
            Run `ccs restart --do` on a throwaway       · 5d · claude-sessions
  4d81aa07  Cmux session sidebar
            Wire the close button to a CCS primitive    · 9d · t3code

Expect it to be short. After the re-enrich, most of today's 219 continue verdicts should collapse to complete or archive once the model can see the branch is gone; the measured floor of genuinely live feature-branch work is 18.

enrichment_title joins the canonical resolver

ADR-0093 made resolveSessionTitle() the single place a session's display title is decided, specifically so seven surfaces could not drift again. enrichment_title shipped days later and is not in that chain — it is read ad-hoc at render-tab.ts:204 and App.tsx:438, and is invisible to ccs ls, ccs session, ccs meta, and the preview. That is the drift the ADR exists to prevent, reintroduced. 

live → custom → role → enrichment → native → codex → fallback

Slotting it above native keeps a human choice winning while letting a title written from how the session ended beat one guessed from how it opened, which is the field's entire argument. Both ad-hoc reads get deleted. state and next stay out of list views — that is what ccs next and the dossier are for.

Already true on master — the hazard runs the other way · 2026-07-26

src/title.ts does not exist on master; it is uncommitted work in the primary checkout. What master has is displayTitle() at src/catalogue/db.ts:1311, which already resolves custom → enrichment → indexTitle, and both ccs ls (cli.ts:586) and the TUI (App.tsx:437) route through it. There is exactly one enrichment-title read in the tree and no drift.

So this decision needs no code here — but it inverts into a merge hazard. The unlanded resolveSessionTitle() omits enrichment from its chain, so merging it as written would regress what master already does: v40 titles would silently stop appearing in ccs ls, ccs session, and the preview. Whoever lands ADR-0093 must add enrichment between role and native.

Two numbers per field: the cap the parser enforces, and in grey the length the schema description actually asks for. The gap between them is the whole point. Caps are a backstop against a runaway generation filling a column; they are not a style guide, and one set at the requested length is not a backstop but a rejection rule for anything that overshoots by a word. That is not hypothetical — v39 capped summaries at 600 characters while telling the model nothing, and rejected two thirds of real sessions for writing three ordinary sentences. Moving the asked-for lengths into the descriptions and the caps out of the way took first-pass success from 33% to 93%.

An earlier draft of this table listed next at a cap of 120 while the decision above asks the model for ≤120 — the identical mistake, one revision later. The caps shipped above the targets, and enrichment-schema.test.ts now asserts that a response written to the asked-for length parses, and so does one 80% longer.

Cutover

Hard: add the new columns, re-enrich all 469 in one sweep, then drop the old ones. Roughly 13k input and 150 output tokens per session — free on the Sol gateway, single-digit dollars metered, about an hour at concurrency 3. The backfill is already complete (469 candidates, 468 enriched, zero at the attempt cap), so this is a known, bounded quantity rather than an open-ended drain.

The alternatives are traps the freshness rule sets. A dual-read transition means two shapes and two render paths forever, because idle sessions never re-enrich on their own and would sit on the fallback path permanently. A mechanical column copy (summary → history, outstanding → next) is instant and free, but leaves chronicle-shaped prose in a state field, comma-chains in next, and no world block anywhere — and the same freshness rule guarantees those rows are never revisited. Either one migrates the problem instead of fixing it.

How the cutover is actually triggered · 2026-07-26

No --force flag was added. v39 already had the mechanism: a row missing a field that did not exist when it was written is incomplete, not fresh, so the sweep is its own backfill. v40 rides the same branch, which means the cutover needs no one-off script and leaves behind no blunt flag that could re-enrich the entire store by accident later.

One subtlety made it work. enrichmentFrom falls back to the v39 text so no panel goes blank mid-cutover — which means state is non-empty for a legacy row, and the obvious !state check would have reported the whole store fresh and quietly done nothing. The row carries an explicit legacyShape flag for the staleness check to read instead; staleness.test.ts pins it.

Why v41 cannot follow immediately

The plan sequenced this add → sweep → drop. The drop has to wait. Readers that predate v40 select enrichment_summary and enrichment_outstanding straight out of SQL — the ccs-go dossier is one — so setEnrichment now dual-writes, copying state and next into the old columns as well. Those readers stay correct and current throughout, at the cost of the old columns living until every one of them has moved across. Dropping them the moment the sweep finished would have broken the panel this work exists to improve.

5 · The outage this measurement found

Fixed 2026-07-26, before this plan was written

The sweep had been dead for about five hours, crash-looping every fifteen minutes with 42 logged failures: index schema version 12 is newer than supported version 11. The launchd plist pointed at the .claude/worktrees/session-enrichment worktree — its own comment flagged that as a stopgap on the grounds that "the deployment has no ccs enrich at all." That premise had expired, and meanwhile the live index cache moved to v12 while the pinned worktree stayed on v11.

Repointed to ~/Programming/Deployments/claude-sessions/bin/ccs, preflighted with enrich --list before reloading, and confirmed live: a 19/19 sweep ran, the stale queue fell to 8, and the only failures were two transient gateway 500s — which the transient-vs-permanent split correctly declines to count against any session's attempt budget.

This is the second time this feature has failed by writing into a log nobody reads; the first was the original plist pointing at a deployment that predated the enrich command. So v40 persists the sweep's last success and surfaces it: ccs enrich --list and the top of ccs triage print how long ago the sweep last succeeded and how many runs have failed since. A pipeline whose entire job is keeping the store legible should not be able to die quietly, and it has now demonstrated twice that it can.

The freshness rule itself is not changing. 457 of 468 rows are current, which is the rule working; the eleven that were not are the outage, not the policy. Tightening to "any movement past an hour" would spend calls summarising sessions you are actively sitting in — the ones you least need a summary of.

7 · Risks and open items

  • The re-enrich is a one-way door on 468 rows of existing copy. Dropping summary and outstanding after the sweep means the old text is gone. Mitigation: back up catalogue.db before the migration, as was done at user_version 37 for v38 — the store's existing habit, and cheap.
  • The register change could overcorrect. "Dry, no hedges, metrics only when they matter" is exactly the instruction a model can take too far, dropping a branch name or a blocking condition as decoration. The section 1 example is the calibration target; the first 20 rows of the sweep should be read before letting the remaining 449 run.
  • The world block adds a filesystem read to a path that previously had none. Reading git plumbing files avoids the process-spawn prohibition, but packed-refs parsing is fiddly, and a repo in an odd state — bare, submodule, Gitfile worktree — must degrade to "unknown" rather than throw. The successor-session count has no such failure mode, which is part of why it carries the coverage.
  • Retired: the cwd trio stays dormant indefinitely. The registry is installed with 31 locations, so the cwd path is live and exercised from the first swept session — the opposite of dormant. What remains dormant is the gate, which only fires on a machine with no registry.
  • Nothing structurally prevents the plist divergence recurring. The deployment now carries enrich and index v12, but the next time the deployed line moves for an unrelated reason, the same drift is available. The preflight in the plist comment is a procedure, not an enforcement; the sweep-health surface in section 5 is what actually catches it.
  • The launchd agent is stopped, and restarting it early would silently undo the cutover. It points at the deployment, which is still v39 code: its setEnrichment does not write enrichment_state, so every session it touched would be re-marked as legacy-shaped and re-queued forever. It must stay down until this branch deploys. The catalogue itself is forward-compatible — v40 is additive and the older binary reads it without complaint — so nothing else breaks in the meantime.
  • Two files claim ADR-0091. This branch has 0091-role-model-policy-is-a-birth-only-compiler-contract.md; the primary checkout has an uncommitted 0091-session-hygiene-commands-ship-as-a-user-scope-plugin.md. The superseding note recording the session-park retirement belongs on the second, and was not written here because the file is not on this branch and creating it would cement the collision.

Two defects the live run found, both mine

A validator that rejected correct answers

The first full sweep failed 33 of 471 sessions, and 18 of the 19 logged failures were a single rule I had invented: remaining must not appear without next, on the reasoning that the first action belongs in next. The rule was simply wrong. A finished session can carry optional leftovers with no obligation attached — "optionally delete the private key now that it is in the Keychain" is a real example from the store — and forcing that into next invents work the session does not have.

This is the v39 length-cap defect wearing new clothes, one revision after that plan recorded it: a constraint the model keeps violating because the constraint, not the answer, is mistaken. Removing the rule and re-running recovered 32 of the 33. The general lesson is worth more than the fix — when a coherence rule fires often, suspect the rule first.

The migration nearly staled the surface it exists to improve

setEnrichment stopped writing enrichment_summary, and readers that predate v40 select that column straight out of SQL. Rows kept their old text rather than going blank — an UPDATE leaves unlisted columns alone — so the ccs-go dossier would have shown a stale description beside a fresh one, indefinitely and silently. The transitional dual-write fixes it forward; 443 already-swept rows were backfilled to match.

Diverged from the plan

  • Merge state and worktree dirtiness were not achievable as specified — see the correction in section 3. Shipped the readable ~89%.
  • The locations registry was already installed, so the cwd gate is inert here and the feature is live rather than dormant.
  • The title-resolver decision needed no code — master already does it. It inverted into a merge hazard against unlanded work.
  • No --force flag. The cutover rides the existing incomplete-row staleness branch, which required an explicit legacyShape flag to work through the compatibility fallback.
  • Caps shipped above targets, not at them, contradicting this plan's own shape table and following its own reasoning.
  • v41 cannot follow the sweep — the dual-write keeps old readers correct, and dropping the columns has to wait for them.

Left open

  • The launchd agent is stopped and must stay down until this branch deploys. It points at the deployment, which is v39 code: it does not write enrichment_state, so every session it touched would be re-marked legacy-shaped and re-queued forever. This is the one action that would quietly undo the migration.
  • The git allowlist decision for merge state and dirtiness.
  • The ccs-go dossier, on another session's branch; correct but not enhanced.
  • v41, dropping enrichment_summary and enrichment_outstanding once the last pre-v40 reader has moved.
  • The superseding note for session-park, blocked on the ADR-0091 collision.
