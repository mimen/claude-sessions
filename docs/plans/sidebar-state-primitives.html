The sidebar's state layer, rebuilt from primitives up

Break the sidebar's "current state" into eight independently owned, independently tested state primitives, give each one a monotonic revision and a cheap change signal, and only then reassemble them — first behind the existing snapshot API, then into a new native SwiftUI sidebar built in parallel. The web sidebar keeps working throughout.

Why it never feels live — the structure, not a bug

One snapshot build (src/sidebar/snapshot.ts) runs seven sequential phases, and each phase carries its own independent cache with its own expiry:

PhaseSourceCost when coldStaleness window
Liveness bridgecmux tree (cmux's JSON of what surfaces exist) + the hook store (cmux's file binding each surface to its session id)one subprocess + file read≤ 2.5 s served-warm, longer under refresh

Three consequences fall straight out of this shape:

1 No component knows that something changed — only how old its answer is. Freshness is bought by re-running everything on a timer.

2 A change anywhere either pays the full multi-subprocess rebuild or serves every column stale together, even the ones that were free to refresh.

3 Correctness rules are smeared across the orchestrator instead of living with their data — which is exactly why identity disagreements between catalogue and index produced dead clicks and doubled hover paint before the liveness ledger landed.

What master already fixed — carried forward, not rewritten

The last week of work on origin/master (local checkout is 71 commits behind) already built real pieces of the target:

  • src/cmux/events.ts — a scoped subscription to cmux's own change events. The push signal for short-horizon state exists.
  • src/sidebar/change-monitor.ts — converges cmux events and SQLite header probes onto "each source exposes one monotonic revision". This is the seed of the revision contract below.
  • The liveness ledger (commit 8e2f98b) — one alias graph joining catalogue + index identities so projection, open, and close answer with a single voice, plus action-vouched short-horizon liveness.
  • A native client exists — macos/CcsSidebarApp/ on master ships the SwiftUI ExtensionKit shell whose SnapshotClient consumes the production snapshot API. The Swift renderer is not greenfield.
The rebuild therefore keeps these mechanisms and promotes their pattern: today the revision idea lives inside one monitor feeding one monolithic snapshot builder. The work is extracting it into named primitives that each own their own signal, contract, and tests.

The eight primitives

Each primitive is a module with the same shape: an idempotent read(), a monotonic revision that advances iff the value could have changed, a change signal appropriate to its source's cost, a written freshness budget, and an explicit failure posture. Nothing else may read its source directly — that rule, enforced like the existing mutation-boundary test, is what makes each piece reliably testable in isolation.

The revision contract — how composition stays cheap

The snapshot stops being "seven caches and a timer" and becomes a pure fold over primitive values, memoized on a composite revision:

primitive      revision   change signal            cost of noticing
─────────────  ────────   ────────────────────     ────────────────
surface tree     r₃ ─┐    cmux events (push)       ~0
hook bindings    r₂ ─┼─►  fswatch (push)           ~0
liveness         r₅ ◄─┘    derived                  ~0
agent activity   r₁ ─┐    hook store + sweep       ~0 / subprocess on demand
catalogue        r₄ │    PRAGMA data_version      ~µs
transcripts      r₆ ─┴─►  PRAGMA data_version      ~µs
workspace extras r₇       scoped events + TTL      subprocess, batched
directory facts  r₈       immutable LRU            ~0
                     │
                     ▼
        composite = (r₁..r₈) ──► memoized snapshot bytes
                     │                    ▲ rebuild ONLY if any rᵢ moved
                     ▼                    └── ETag compare unchanged otherwise
             Swift / web clients

Polling a revision vector is microseconds — header probes and integers, no subprocesses — so the server notices any change within ~100 ms and rebuilds only the parts that moved. Clients (both) stay on conditional GET against the ETag they already use; nothing about the transport changes. This is the "layered watchers" decision applied literally: instant where the kernel gives it to us free, scheduled sweeps only where a subprocess is unavoidable, and never a poll that re-reads what a revision proved unchanged.

Ground truth first — assume the tracking is wrong

Every primitive above is validated not just for internal consistency but against an oracle measured independently of ccs. The working assumption is that some of the eight are tracking reality inaccurately today — possibly all of them, and the UX problem may be a redraw bug sitting on top of correct data. Both get tested, and the harness separates them:

1Surface treeWhat cmux itself displays: independent cmux tree invocation + visible windowsevery surface we show exists; every real surface we list
2Hook bindingsThe bound session's transcript file exists and a claude process is actually running on that surface (ps by tty/pid)binding ⇔ live process
3LivenessHuman-visible: the pane a row claims is live really holds that session; a dead row's workspace holds nothingspot-check script over all rows
4Agent activityScripted sessions driven through known states (mid-run, stopped-and-waiting, idle) while sampled"Needs input" fires exactly when the agent actually waits
5Catalogue identityBehavioral: clicking the row focuses the tab that actually owns the session; resume lands on the right lineageresolve-then-act equals intent
6Transcript factsThe Store files themselves: line count vs our message counts, direct usage-line math vs our cost, file mtime vs our recencywithin stated tolerance
7Workspace extrasActual unread content in the panebadge ⇔ real unread
8Directory factsgit run in that directorybranch/worktree exact

This runs as a continuous differential harness during soak (a ccs sidebar verify mode), logging every disagreement into a discrepancy ledger. Each discrepancy is classified four ways — because "the data is wrong" and "the data was right but never reached the screen" have opposite fixes:

discrepancy class        meaning                              fix lives in
───────────────────────  ───────────────────────────────────  ─────────────────
A  source wrong          primitive misreads its source         the primitive's parser/read path
B  signal wrong          source changed, revision didn't move   the change signal / watcher
C  composition stale     revision moved, snapshot not rebuilt   the fold / memoization
D  render stale          client got fresh bytes, drew nothing    the client redraw path

Class D gets its own cheap instrumentation regardless: both clients log the last revision they received and a hash of the bytes they rendered, so "server advanced but screen didn't change" is provable from logs rather than argued from vibes. If the soak comes back clean across all eight, we'll know the tracking was accurate and the liveness complaint was purely classes C/D — which the revision contract then eliminates by construction.

The testing ladder — reliability before reincorporation

Each primitive must clear all five rungs before anything consumes it again:

0Ground-truth oracle. Differential validation against reality measured without ccs (table above) — run first, since a perfectly tested primitive tracking the wrong thing is worse than an untested one.

1Parser units. Fixture-based, no I/O — the pattern status.ts already uses, applied everywhere.

2Fake-source behaviour tests. Each primitive takes its source as an injectable interface; tests drive real sequences (bind → resume → close; commit → probe → miss) under a fake clock, asserting both value and revision movement.

3Fault injection. For every primitive, scripted hostility: subprocess timeout, torn/partial file write, unreadable DB, source vanishing mid-read. Assert the documented failure posture and that revision never advances on a failed read (a failed read must never look like a change).

4Live soak + bench. Extend the existing src/sidebar/bench: record real cmux event streams and DB traces, replay them, and assert (a) end-to-end perceived latency under budget, (b) zero rebuilds when nothing changed, (c) no event-loop blocks, (d) a clean discrepancy ledger against the oracle. The bench numbers become the acceptance evidence on this page.

One cross-cutting guard joins them: a contract test compiling the TypeScript snapshot type against the Swift Snapshot.swift Codable struct in CI, so the native client and the state layer cannot drift silently.

Build order

1Baseline instrumentation + ground-truth sweep. Measure today's numbers (per-phase latency, staleness windows, rebuild frequency) and run the differential oracle across all eight primitives against live state — this is where we learn which tracking is actually inaccurate before extracting anything.

2Primitives 1–2–3 (tree, bindings, liveness). Highest correctness stakes — this is where the historical dead clicks and doubled rows came from. Extract from the existing bridge + ledger code, add fault-injection suites.

3Primitives 5–6 (catalogue, transcripts) including killing the synchronous message-count pass permanently with the visible-row tail-counter.

4Primitives 4, 7, 8 (activity, extras, directory) with the layered activity watcher replacing the unconditional status fan-out.

5Recomposition. snapshot.ts shrinks to the revision-fold; change-monitor becomes the driver; endpoints and ETag semantics unchanged. Web sidebar rides the new engine without knowing.

6Native SwiftUI build, in parallel from step 2 onward. The renderer consumes the unchanged snapshot API from day one; feature work happens there, the web app freezes as fallback. Dock cut-over when the soak ladder passes against the native client.

Decisions settled

DecisionChoiceRunner-up and why it lost
Target surfaceNative SwiftUI sidebarWeb-first — rejected because the direction to native was already declared on the branch and the native shell exists on master; building primitives surface-agnostically makes web the free fallback rather than the goal.
Liveness mechanismLayered watchers per primitiveCentral push bus + SSE — rejected because the measured transport shows unchanged polls are already zero-body 304s; push adds reconnect machinery before the cheaper win (revision-probe polling) is exhausted.
RolloutNew parallel Swift build; web keeps running on the recomposed engineBig-bang replacement — rejected: loses the working Dock sidebar for the arc and concentrates all reliability learning at the end instead of per-primitive.
Where state logic livesTypeScript server owns all state; Swift only rendersNative Swift reading SQLite/hook store directly — rejected: duplicates four battle-tested adapters behind one IPC boundary and splits correctness rules across two languages.

Risks stated plainly

  • Some of the eight probably track reality inaccurately today. That is the working assumption, not a risk: the ground-truth sweep in phase 1 exists to find out which, and no primitive graduates its ladder while its oracle disagrees with it.
  • cmux event coverage is unproven for every field. If events miss a transition (e.g. a status flip with no emitted event), the layered design catches it on the next reconcile sweep — but the freshness budget for that field is then a lie (a class-B discrepancy). The soak ladder measures this per field.
  • Revision-probe polling still wakes the process 10×/s. Measured in baseline instrumentation; if it shows up in energy, the probes collapse into fewer timers without changing the contract.
  • The local checkout is 71 behind master. All work starts in this fresh worktree; the exploration numbers above come from pre-master-71 code and get re-verified during baseline instrumentation.
  • ExtensionKit sidebar constraints (sandboxing, memory limits) bound what the Swift app can do; the render-only posture keeps those limits away from the state layer by construction.
