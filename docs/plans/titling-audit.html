Every way a Claude Code session acquires a display name — who owns each source, how it's generated, where it's stored, and the order they resolve in. Part I is the audit (how it works today). Part II (§10–12) diagnoses the inconsistencies and proposes a simpler, single-source model.

TL;DR — the end state we're proposing (read this, skip the rest if you like)

Every ordinary session shows one title, picked from the best source that exists, in this order:

  1. the name you gave it — typed, or via /ccs:suggest-title. If it exists, it wins. Always.
  2. Claude Code's auto-name (the ai-title the harness writes)
  3. ccs's generated name (the titler's guess from the transcript)
  4. the first message, cleaned up — or "untitled" if there's nothing usable

Plus two guarantees that don't hold today:

  • Same name everywhere — list, TUI, ccs meta, the tab all agree. (Today they can disagree, or show blank.)
  • Your name is permanent and always wins — no machine guess overrides it, no cache-clear loses it. (Today the TUI t key can silently no-op and can be wiped by an index rebuild.)

Why it's the floor: a title must be findable (your name is permanent + top priority), honest (same everywhere), and never worse than now (intentional beats generated beats nothing). You can't satisfy fewer than these three.  Scope: ordinary sessions only — role/cluster worker tabs keep their own naming, untouched.

How we get there — three steps, smallest and safest first

  1. Make "name it yourself" always stick. (small, do first) The TUI t key writes to the throwaway cache today and can silently no-op; point it at the permanent store, like /ccs:suggest-title already does.  → naming a session is permanent and always wins.
  2. Make every screen read the title the same way. (the keystone) Replace ~7 drifting title-picking sites with one function that applies the 4-step order above; every screen calls it.  → list, TUI, ccs meta, tab all agree; the ★/✎ marker stops lying. This is where the ordinary-vs-identity boundary is drawn in code.
  3. Fix the misleading name. (free, anytime) Rename/document native_title (it means "last-shown title," not "the AI title").  → no one is misled later. Doc-only.

Why this order: each step ships alone and is useful alone (never half-migrated); smallest/safest first, so you get value before the bigger change; step 2 is a pure reorganization (no schema/data change) over tested code; and none of it touches the cluster/worker naming.  The pr-watch PR-title cleanup is a separate, later track — it reaches into another system.

1 · The one thing to understand first

A session does not have a title. It has up to six candidate strings from four owners, and two different display surfaces (the ccs list/TUI, and the cmux tab) resolve them in different priority orders. "What's this session called?" has two correct answers depending on where you look.

Three of the candidates live in the rebuildable index (~/.ccs/cache/index.db, reconstructable from transcripts), one lives in the durable catalogue (~/.ccs/cache/catalogue.db, never dropped), one is an identity attribute, and one is only ever live in cmux. That split is why clearing a custom title "loses" nothing — the index still holds the fallback chain.

3 · Resolution order — the two surfaces disagree

Surface A — the ccs TUI (fullest chain)

src/index/index.ts:70 · src/tui/App.tsx:328

The index resolves a base title by SQL COALESCE; the TUI then layers the catalogue's durable strings on top:

  1. live cmux tab title if the session is open — what cmux currently shows
  2. custom_title — your explicit title
  3. role — identity role name
  4. native_title — Claude Code's ai-title
  5. codex_title — ccs-generated
  6. fallback_label — cleaned first message → "(untitled)"

Items 4–6 are the COALESCE(native_title, codex_title, fallback_label) the index returns as title; items 1–3 are layered in front of it by App.tsx (openTitles ?? customTitle ?? role ?? r.title).

ccs ls is a subset of this — cli.ts:506 — it does only custom_title ?? resolved, with no live-cmux layer and no role layer. So a role loop with no custom title shows its role name in the TUI but its native/codex/fallback title in ls.

The write-through loop: cmux → custom_title

App.tsx:335 — while a session is open, the TUI persists its live cmux tab title back into custom_title (guarded so a slug-shaped id can't poison it). So a cmux rename doesn't just paint the tab — it durably becomes the session's title. This is the reverse direction of surface B (where ccs paints the tab from custom_title), and the two together are why titles converge across list, TUI, and tab once a session has been open in cmux.

Surface B — the cmux tab, painted by ccs

src/catalogue/render-tab.ts:201 (loops) · :220 (work sessions)

When ccs paints a tab (turn hook or ccs sync-tabs) it uses a different, shorter chain — the index fallback chain isn't consulted at all:

  • Loop/role session: custom_title || role || identity-key || id[:8]
  • Work session: meta.shortname || custom_title (with #PR prefix composed on) || identity-key || role || id[:8]

Consequence: a tab and the list can show different names for the same session

If a session has only a native_title (no custom title), the ccs list shows that native prose, but a ccs-painted tab falls through to the identity key or id[:8] — because render-tab never reads native_title. In practice the tab usually still shows the native prose anyway, because cmux itself set the tab from Claude Code's ai-title and ccs only repaints on sync. The ✳ you saw prefixed to your tab is cmux's own activity glyph, not a ccs title source.

Surface C — the Claude Code statusline

src/catalogue/render-statusline.ts:56

A third surface, the bottom-of-window status line, composes its own label: a work tag (#PR / W-…) + custom_title (PR-prefix stripped) + a state pill. Same custom_title-first bias as the tab; the index fallback chain doesn't reach it either.

4 · How native_title is captured

src/parse.ts:147

if (obj.type === "ai-title" && typeof obj.aiTitle === "string") {
  nativeTitle = obj.aiTitle;   // reassigned every occurrence → LAST one wins
  continue;
}

The record repeats on essentially every turn (Claude Code re-emits the current title each line). ccs takes the last, so if the title changed mid-session the newest value is kept. This is the field that carried kebab-case slugs in 4 of your transcripts — those sessions were renamed to a cmux worktree slug partway through, and that slug flowed back into the ai-title channel. ccs never writes ai-title records; it only reads them.

5d · When titling runs, and who is eligible

src/index/index.ts:260 (gating) · src/titler/queue.ts:32 (drain) · src/tui/App.tsx:564 · src/cli.ts:400

Three triggers drain the queue: the TUI in the background on launch, ccs reindex --titles (the cron/launchd path), and the TUI t key on one row. A session is a candidate only when:

native_title IS NULL          -- never override the harness title
AND is_subagent = 0           -- subagents aren't titled
AND title_attempts < maxAttempts   -- default cap 3; failures don't retry forever
AND skeleton <> ''            -- needs content
AND ( codex_title IS NULL     -- never titled, OR…
      OR msg_count > title_msg_count * 1.5 )   -- grew >1.5× since last titling → regenerate

That last clause is the one place a ccs-generated title regenerates as a session grows — unlike the harness ai-title, which is written once and (absent a rename) never revisited. Concurrency defaults to 3; a successful generate stamps title_msg_count and resets attempts.

6 · How fallback_label is cleaned

src/label.ts · src/index/index.ts:194

Pure string surgery over the first human messages, no model. In order: return a bare /slash-command as its own name; else strip harness <command-*> / <local-command-*> wrappers and any stray tags; drop leading pasted file-path lines; collapse whitespace; truncate at 80 chars with …. If every candidate cleans to empty → "(untitled)". This is what shows for the ~92% of sessions with neither a native nor a generated title.

8 · Findings surfaced during the audit

Observations, not proposed changes. Each is a real behavior worth knowing; whether any is worth fixing is a separate call.

F1 · ccs meta / ccs session show only custom_title, not the resolved title

commands.ts:600 · session-command.ts:119 — both print the catalogue's custom_title and nothing else, so a session whose real name is a native/codex/fallback title shows a blank title: line (or -). This is why clearing this session's custom title made ccs meta go blank even though ccs ls still showed the native title. It matters because /ccs:archive and /ccs:info read the title from ccs meta — on the ~2/3 of sessions with no catalogue row, they'd see no title and retitle unnecessarily. The fix would be one titleOf() fallback at each site.

F2 · TUI t and /ccs:suggest-title write different fields

App.tsx:734 vs the slash command → ccs rename — the TUI t key stores a codex_title (index); the slash command stores a custom_title (catalogue). Same generation, different storage and different precedence. The slash-command form is durable and overrides native; the t form is a rebuildable-cache write.

F3 · On a native-titled session, TUI t is a display no-op

Because display resolves native before codex, pressing t on one of the ~7.7% of sessions that have a native title generates and stores a codex_title that is then permanently shadowed and never shown. The background/reindex path avoids this (it gates on native_title IS NULL); only the manual key bypasses the gate. /ccs:suggest-title does not have this problem — custom_title outranks native.

F4 · Native titles are rare and effectively immutable

Measured on this host: 363 of 4,711 transcripts (7.7%) carry any ai-title; of those, 359 never change it. The 4 that "changed" were renamed to cmux worktree slugs, not re-generated. So the harness titles the opening ask, once — which is exactly why ccs needs its own titler for the other 92%, and why a native title is usually the earliest, most stable name a session has.

Part II — Analysis & a simpler model

The audit above shows a system that works but has accreted. The problems aren't the number of title sources — the provenances are all genuinely distinct and worth keeping. The problems are in the plumbing. And the first, biggest simplification is to recognize that two different naming systems have been tangled into one.

Scope decision — two naming domains, split apart

There are really two kinds of "title," and this refactor only touches the first:

Session title IN SCOPEIdentity name OUT OF SCOPE
Answers"what was this conversation about?""which durable responsibility is this?"
Applies toordinary one-off / ad-hoc sessionsrole loops & cluster work-units (pr-watch, event-watch)
Produced bygenerated (native / codex / fallback) + optional human overridecustomized / authored — never generated
Inputsnative_title, codex_title, fallback_label, human custom_titlerole, meta.shortname, #PR, cluster-synced custom_title, board pills
Owned bythe index resolver + list/TUI/meta displayrender-tab.ts (renderLoop / renderSession) + statusline + catalogue_sync

The identity domain is authoritative and customizable by design — those names are deliberately set by an operator or a cluster, so "unify the resolver" and "single-writer" don't apply to them the way they apply to generated titles. It's a separate subsystem (ADR-0089 identities) with its own contract. We split it off and refactor only the one-off session title. Conveniently, the code already half-embodies this: render-tab.ts is the identity renderer; a plain session never routes through it.

10 · Root causes (session-title domain)

Within the in-scope domain, the inconsistencies trace to two structural choices. (A third, RC2, turns out to live entirely in the out-of-scope identity domain — noted below and then set aside.)

RC1 · There is no single "what is this session called?" function

At least seven sites independently decide the display title, and they have already drifted:

To change precedence you must edit up to seven places and keep them in agreement — which hasn't happened (F1 and the ls-vs-TUI gap are live drift). This is the single biggest maintainability cost.

RC2 · custom_title has more than one writer OUT OF SCOPE — identity domain

Recorded for completeness, then set aside. It is written by the human (ccs rename, /ccs:title, the NL command, session set --title) and by the pr-watch cluster's catalogue_sync, which overwrites it with the full PR title every tick (render-tab.ts:223, new-session.ts:46). Because a user title can be clobbered by sync, two workarounds had to be invented:

  • meta.shortname — a second title field that sync won't touch, so a worker's label survives render-tab.ts:242.
  • stripPrPrefix() — because sync bakes #12133 into the stored title, every reader must strip it back off render-tab.ts:216.
  • the write-through's slug guard — because the field can hold sync-shaped junk, the cmux→custom write-through must sniff and reject id-shaped values App.tsx:343.

One overloaded field spawned three defensive mechanisms. The clean fix — give the cluster's synced PR title its own field so custom_title means only "the human's title" — belongs to the identity/cluster subsystem and crosses into ~/.ccs-config. Out of scope for this refactor; tracked as a separate identity-domain cleanup. Note that within the in-scope one-off domain, custom_title already has a single writer (the human) — this problem simply doesn't arise there.

RC3 · A human retitle writes rebuildable storage

The TUI t key stores its result in codex_title, which lives only in the index (App.tsx:734 → saveCodexTitle, index.ts:278). Verified: codex_title is absent from the index INSERT column list and is never re-written on re-parse — so it survives incremental reindex, but a full index.db delete (which README explicitly says is safe) loses it. A title a human deliberately chose should not live on a cache the tool promises is disposable. This one choice causes F2 (two fields for one gesture) and F3 (native shadows codex, so t silently no-ops on the 7.7% with a native title).

12 · Proposed model — one session-title resolver, one invariant

Proposals for the in-scope (session-title) domain only. None is authorized; each ships independently, smallest-blast-radius first. All are entirely inside this repo — none touches the cluster contract.

P1 · One canonical resolveSessionTitle(row) fixes RC1, F1, ls-drift, G1

A single pure function returns the display title for a one-off session — just the four generated/human inputs, no identity fields:

custom_title → native_title → codex_title → fallback_label

Every session-domain surface calls it — titleOf, ccs ls, the TUI list base, ccs meta, ccs session, the preview. F1 and the ls-vs-TUI drift vanish by construction, and the ★/✎ source glyph is computed from what actually won so it stops lying (G1).

The domain boundary is explicit, not merged. For a row that has an identity (role / cluster / work-unit), display defers to the identity naming layer (render-tab, unchanged): the shared list merge drops its inline ?? role and instead branches "identity row → identity name; plain row → resolveSessionTitle." The live-cmux write-through stays as-is; it just feeds custom_title.

Effort: medium · Risk: low — pure-function extraction over a well-tested surface, no schema change. Keystone: do it and F1/G1/ls-drift close together.

P2 · Provenance invariant: machine→index, human→catalogue fixes RC3, F2, F3

Enforce one rule: machine guesses live in the rebuildable index; authoritative human choices live in the durable catalogue. Concretely, point the TUI t key at custom_title (like the slash command already does). Then:

  • codex_title becomes purely the automated-backfill field — never written by a human action, safe to lose on an index rebuild;
  • a human retitle is durable and outranks native, so t works on every session (F3 gone) and matches /ccs:suggest-title exactly (F2 gone).

Effort: low · Risk: low — one call-site change plus a row reload. Best impact-per-line, and a clean first step.

P4 · Document (or rename) native_title fixes N1

Rename to harness_title / emitted_title, or at minimum document that it is "the session's last-emitted display title, harness- or externally-set" — so the next reader doesn't assume it's always AI prose. Doc-only; near-zero risk.

Deferred, separately: P3 · single-writer custom_title identity domain — not this refactor

The cluster-sync-clobbers-custom_title problem (RC2 / W1) and its fix — give the synced PR title its own field, retiring meta.shortname, stripPrPrefix, and the slug-guard — live in the identity/cluster subsystem and cross into ~/.ccs-config. Real cleanup, arguably higher value, but a different effort with a cross-system contract. Tracked here so it isn't lost; excluded from the session-title refactor by the scope decision above.

What this collapses to (in scope)

After P1, P2, P4 the one-off session title reduces to: four stored provenances (harness / codex / fallback / human), one resolver, one clean rule for which store a title lands in. The session-title chains collapse to one; F1, F2, F3, G1, N1 all close. No source is removed, and the identity naming system is left untouched behind a clear boundary.

Recommended sequence — all in-repo, low-risk

P2 first (tiny, self-contained, fixes F2+F3) → P1 (the keystone; makes every session surface consistent, absorbs F1 + the ls drift + G1) → P4 (doc, free). None touches ~/.ccs-config. The identity-domain P3 is a separate, later track if you want it.

What changed in this doc

  • Scope decision (§Part II preamble): split the two naming domains. Session title (generated + human override, for one-off sessions) is in scope; identity name (role / cluster / PR-worker, authored not generated) is out of scope and left untouched. Verified the boundary is clean — render-tab.ts is the identity renderer; a plain session never routes through it.
  • Rescoped §12: P1 is now the session-title resolver only (defers to identity naming for identity rows, rather than swallowing it). P3 (single-writer custom_title) moved out of scope into the identity domain, since its dual-writer only exists for cluster sessions. Result: the whole in-scope plan (P2 → P1 → P4) is in-repo and low-risk.
  • Earlier: added the Part II diagnosis, inconsistency catalogue, and verified claims (codex_title lost on index rebuild; catalogue_sync a second writer of custom_title).
