1 · What this is for

The session store has grown past the point where a transcript is a useful way to remember what a session was. Opening one shows the last few hundred lines of tool calls; catching up means reading. With 458 top-level sessions, catching up doesn’t happen.

Enrichment replaces that with a cached, structured description generated once per session: a short summary, what’s still unfinished, a recommended next action, and a judgement about whether the session is even running in the right directory. It is generated by one model call, stored on the session’s catalogue row, and regenerated only when the session has actually advanced.

2 · The decisions that shaped it

Five questions were open when this thread started. Answering them moved the feature from “a Go TUI reads its own sidecar database” to “CCS owns enrichment as first-class state.” Each decision below records what was chosen and what was rejected, because the rejected option is usually the one a future reader would otherwise re-propose.

Enrichment lives in catalogue columns, not a sidecar or a JSON blob

The original design gave the Go TUI its own SQLite file to avoid touching the CCS schema, with a migration to “canonical storage” deferred. But the catalogue is at user_version 37 with roughly twenty additive ALTER TABLE catalogue ADD COLUMN precedents, each presence-guarded, and since b9760e7 every migration runs in one transaction with a post-migration schema check. Adding columns here is routine.

Rejected: a ccs-go sidecar. It makes enrichment invisible to the statusline, ccs ls, and every other consumer, and turns “promote it later” into a scheduled migration. Also rejected: the generic meta JSON blob. meta is explicitly scratch state that ccs stores without interpreting; enrichment is the opposite — state that wants to be queried, sorted, and indexed.

CCS owns the producer; the TUI is only a reader

Once enrichment became catalogue state written through a sensor path, the model call belonged in CCS too — mirroring ccs reindex --titles. This turned out to shrink the build rather than grow it: src/start/gateway.ts was already a working, zod-validated gateway client, so there was no new inference engine to write in either language.

Rejected: the Go TUI owning the model call. It strands inference logic in a language no other consumer speaks, so the next reader — statusline, cron, the board — reimplements it.

Working-directory suggestions are registry keys, not free text

Sessions are often started in the wrong place, so enrichment judges whether the cwd fits the work. Asked openly, a model answers with a plausible invented path — the first real run on this machine, with no registry installed, proposed ~/.claude/skills/ccs-new for work that belongs in the CCS repo. Constrained to the shared launch-location registry (30 curated locations with verified paths), the model picks a key that can be checked, and the same run correctly proposed ~/Programming/Repos/claude-sessions.

Rejected: free-text paths everywhere. Kept only as the escape hatch for work with no registered home — which is itself the signal that a location should be registered.

No delete, and no fourth status enum

CCS has no delete: lifecycle is a fixed enum over an append-only forensic record. Rather than build destructive deletion so a model could recommend it, the enum stops at four values and a separate junk boolean preserves the “never worth starting” distinction. A status field was dropped entirely — the catalogue already carries lifecycle, stage, and activity, and a fourth status-shaped axis is one more thing to keep coherent for no new information.

Rejected: archive + a junk entity tag. ccs tag links sessions to vault entities; junk isn’t one, and putting it there is a permanent semantic leak.

Freshness is driven by progress, not by a clock

A session is re-enriched when it has gained 10 messages, or when it has moved at all and the stored summary is more than six hours old. An idle session is enriched once and then never again, which is what makes the steady-state cost approximately nothing.

Rejected: “re-enrich when last activity moved,” which appeared in the original design alongside the message threshold. Any session that gains one message has moved, so that rule would have fired on every advance and made the threshold decorative. The case it was reaching for — a dormant session picked back up — is caught by the age backstop instead.

3 · How it works

The stored shape

Eleven columns on catalogue, all prefixed enrichment_. Two of them — enrichment_at and enrichment_at_messages — are the provenance that makes staleness computable, and are asserted by the post-migration schema check.

ColumnMeaning
enrichment_titleA name derived from how the session ended, not how it opened (v39)
enrichment_summaryTwo or three sentences: what the session was, where it ended up
enrichment_outstandingOne line on what is still unfinished; empty when nothing is open
enrichment_recommendationcontinue · complete · archive · handoff (CHECK-constrained)
enrichment_reasonOne line justifying the recommendation
enrichment_junkNever worth starting — distinct from a real attempt that failed
enrichment_cwd_correctWhether the cwd suits the work the session actually did
enrichment_suggested_locationA registry key, when the cwd is wrong
enrichment_suggested_cwdFree-text path, only when no registered location fits
enrichment_at_messagesMessage count at generation — staleness is current − this
enrichment_atGeneration timestamp, for the age backstop
enrichment_attemptsFailed attempts; capped at 3, reset by any success

Recommendation → action

ValueMeansAction
continueLive work worth resumingnone — stays active
completeIt succeeded and is doneccs mark --completed (stays visible)
archiveAbandoned or a dead endccs mark --archived (hidden)
handoffBelongs with another session or personthe handoff skill

The command

ccs enrich [<id|prefix>|.] [--json]        one session, now
ccs enrich --sweep [--limit N] [--concurrency N]
ccs enrich --list  [--limit N] [--json]    what the sweep would do, no model calls

--list exists because the sweep is what a scheduled job runs unattended: being able to ask “what do you currently think is stale” without spending calls is how a cadence gone wrong gets diagnosed. Session ids accept unique short prefixes, so --list output pastes straight back into the command.

Why enrichment mints no sessions

The failure this design avoids

Headless model calls made through a harness binary (claude -p, codex) register as Claude Code sessions. The real store already contains junk one-line entries from exactly this — “Reply With OK”, “Identify the Running Model ID”. Enrichment runs over every top-level session, so a harness-based implementation would have added hundreds of such entries to the catalogue it exists to make legible, and each new entry would itself become enrichable. That is a loop.

Enrichment therefore reaches the model by raw HTTP POST only, which cannot create a session. src/enrich/provenance.test.ts pins this at the source level — it fails if any module under src/enrich gains a process spawn or a harness invocation.

Prompt injection

Enrichment reads conversations containing arbitrary text, including text shaped exactly like a directive to a model. The transcript is fenced in a <session> block and the system prompt states that everything inside it is untrusted data that must never be followed as an instruction — the same stance src/start/gateway.ts takes toward catalogue titles, and more load-bearing here because the payload is a whole conversation. Beyond that, output is structurally constrained: a location key the model was not given is rejected outright.

4 · What it costs

The cost argument is entirely in the cadence. A timer-based sweep would re-read 458 finished sessions every night to discover that none of them changed. Progress-based staleness means the backfill is a one-time expense and the steady state is a trickle.

458 sessions · one-time backfill steady state

Input is bounded per session — a 24k-character transcript tail plus the indexed skeleton, roughly 13k tokens at worst; output is about 150 tokens. On Sol via the ChatGPT subscription the marginal cost is approximately zero; the metered equivalent for the whole store is single-digit dollars. The scheduled job takes 40 sessions per run so a cold store drains in about two hours without ever presenting the gateway with a burst.

What real runs changed

Two defects only appeared against the live store, and both are worth recording because the unit tests could not have found them.

  • Field budgets the model was never told about. Summaries were capped at 600 characters with nothing in the schema mentioning a limit, and two thirds of real sessions were rejected for writing three ordinary sentences. The caps are now backstops (1200/500) and the requested lengths appear in the schema descriptions the model actually reads. First-pass success went from 33% to 93%.
  • Unattended failures were invisible. The sweep reported “failed 8” with no reasons, which in a launchd log makes a dead gateway, an expired key, and one bad transcript indistinguishable. Each failure now logs a truncated reason to stderr.
  • A rate limit was quietly disqualifying sessions forever. The attempt cap exists so a transcript the model genuinely cannot handle stops costing calls — but it was counting transport failures too. One provider cooldown burnt an attempt on forty perfectly enrichable sessions in a single sweep, and twenty-seven had already reached the cap of three, between that and the summary-length bug above. Both causes were mine, not theirs. Transport failures are now a distinct error type that is retried freely and never counted; only an answer the model produced and we rejected spends budget. The counters were reset.
A note on the attempt cap

The general shape of the bug is worth remembering: a budget meant to bound the cost of bad input was being spent on bad infrastructure. Those fail identically at the call site and mean opposite things — one is permanent and about this session, the other is temporary and about none of them. Any retry budget needs that distinction at the point where it decides to count.

6 · Open items and known limits

  • The location registry isn’t on this machine yet. ~/.ccs/locations.toml ships with the /ccs:new session router, still unmerged in feat/ccs-new-router. Until it lands, cwd suggestions fall back to free text and are noticeably weaker; the command warns when it finds no registry. No code change is needed when it arrives.
  • master is 7 commits behind the deployed ccs (14dd6df, carrying index schema v10). This branch is based on the deployed head, not on master. Merging it to master alone would ship a binary that cannot read the live index.
  • The ccs-go work is on its own branch, unmerged. feat/dossier-enrichment branches from feat/navigate-led-redesign, which another session owns. Merging it is that session's call, not this one's.
  • The deployed ccs briefly predated enrich. The first plist pointed at the deployment and would have failed every fifteen minutes with Unknown command. The branch is now deployed and the agent points there, but the installer keeps the preflight that proves the command exists in whatever checkout it is asked to schedule — the failure mode was silent, into a log nobody reads.
  • Two sweeps have no mutual lock. launchd will not start a second copy of its own job, but a manual ccs enrich --sweep run alongside it can enrich the same session twice. Harmless — the write is idempotent and last-write-wins — but wasteful.
