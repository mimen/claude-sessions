Decision record · read only

/ccs:new session router

One command turns an initial prompt into a correctly placed, correctly routed, CCS-managed top-level session. Local births return a concrete session and workspace; remote births report exactly what is known and leave the session ID pending when target-side delivery cannot yet be confirmed.

Status: implementation and release-blocker fixes are committed and locally validated. Router integration and installation remain pending.

The swap-harness dependency is merged. The router branch is not yet pushed or merged, and no runtime link, installed plugin, live session, remote workspace, or Dock control has been changed.

01 · The change

What /ccs:new changes

Today, turning an idea into a running session goes through ccs start, a one-shot inference step that guesses a resume payload before launching. Measured on 2026-07-24, ccs start --explain "Implement a fast new-session router for CCS" took 3.75 seconds, produced an invalid resume payload, and fell back to 0% confidence.

/ccs:new replaces that guess. It is a user-invoked CCS plugin skill (plugins/ccs/skills/new/SKILL.md, reached as /ccs:new through the installed ccs plugin) that reads a deterministic launch-location registry first and only asks a question when the destination is genuinely ambiguous. The invoking session is a launcher: it reads the prompt as a routing request and never performs the prompt as work. Routing, validation, and birth mechanics live in typed CCS code, so no second prompt-only router exists.

/ccs:new becomes the single conversational router. ccs start remains as a deterministic shell shortcut: it opens a fresh CCS-managed top-level launcher and pre-fills /ccs:new in the Claude composer without pressing Enter, ready for the user to finish or edit the request. It contains no routing inference of its own. A local router receipt names the reserved session and workspace; a remote receipt names the SSH workspace and remains explicitly uncertain about target-side reservation and prompt delivery.

02 · Walkthrough

The launch flow, end to end

A submitted /ccs:new run moves through eight stages. The model already running the skill does the interpreting and any asking. A bundled deterministic wrapper only reads the registry, validates candidates, and returns structured JSON. There is no extra inference call. The optional ccs start entry point stops one step earlier: it creates the launcher and leaves the skill text unsubmitted for human completion.

  1. 1
    Interpret, do not execute. The invoking session reads the initial prompt as a request to place and route a new session, not as work to carry out.
  2. 2
    Match the registry. Resolve exact keys, aliases, explicit paths, and deterministic token overlap against registered launch locations.
  3. 3
    Inspect candidate facts. Read the current host's canonical path and Git state, the authored eligible hosts and capabilities, and existing-session warnings. After a remote host is selected, CCS runs one bounded SSH preflight on that target before creating any workspace.
  4. 4
    Clarify only when it matters. If one candidate clearly dominates, launch it. Otherwise the current session presents the small candidate set through AskUserQuestion. No seam model participates.
  5. 5
    Choose placement. Prefer the Mac Mini only when location eligibility, required capabilities, and task-local-state checks pass. If remote preflight fails before any workspace exists, a laptop launch requires a separate explicit user choice after the concrete blocker is shown. Any remote workspace evidence forbids fallback.
  6. 6
    Resolve the route. Pick harness and exact target model from the canonical routing policy through the birth compiler. Because this is a user-managed root session, use ccs session new --top-level, not ccs delegate.
  7. 7
    Create one managed birth. Locally, CCS reserves the UUID and opens one detached cmux workspace with the prompt in the launcher argv. Remotely, CCS opens one local cmux ssh workspace whose command performs the Mini-side managed birth. Nothing is submitted twice.
  8. 8
    Register if eligible, then report. A durable explicit path may be registered only after a structured local status: launched receipt. The report states the machine, cwd, route, and available workspace or session identity without claiming target-side prompt delivery when it is not receipt-confirmed.

03 · Design stance

Three commitments the design holds to

Interpret, don't execute

The launcher routes the prompt; it never runs it as work.

Thin skill, typed core

The skill owns the conversation; CCS code owns routing, validation, and births. No second router in prose.

Latency is a feature

Deterministic registry lookup first, one bounded target preflight when remote, and no extra model call.

04 · Alternatives

Choices that lost, and why

Rejected: a separate inference call (a lightweight seam model such as Luna) to interpret the prompt.

Chosen: the model already running /ccs:new interprets; a dedicated always-alive launcher may run Terra at medium effort.

Why: an extra model call adds latency for no gain. Residual interpretation belongs to the session that already holds the context.

Rejected: reading routes from the legacy ClaudeConfig/claudes launch identities.

Chosen: one curated locations.toml registry; claudes remains intact until every surviving direct-launch capability has a tested replacement, then moves to the vault archive.

Why: outdated identities would compete with the new surface and reintroduce folklore routes.

Rejected: birthing the session with ccs delegate.

Chosen: ccs session new --top-level.

Why: the result is an independently managed root work body, not a subordinate auxiliary child.

Rejected: creating the Mac Mini workspace directly in the Mini's own cmux now.

Chosen: an interim cmux ssh workspace plus a Mini-side ccs session new --inline birth.

Why: the Mini cmux socket requires authentication and its expected password source is absent, so Mini-native creation is not a safe first-version dependency. Issue 34 supersedes the interim transport without changing /ccs:new.

Rejected: preserving the old infer-and-launch behavior, or deleting ccs start entirely.

Chosen: /ccs:new owns all interpretation; ccs start opens a fresh managed launcher and types /ccs:new into its composer without submitting it.

Why: the old inference path was slow and invalid, while a pre-filled composer keeps the shell ergonomics without creating a competing router. The user retains the last edit and submit step.

05 · State boundary

The registry and the cross-machine boundary

One shared registry, ClaudeConfig/session-routing/locations.toml, is the source of truth for valid session CWDs. ~/.ccs/config.toml points CCS at that file and the companion host registry. The machine adapter validates both shared TOML files, then safely creates or repoints ~/.ccs/locations.toml and ~/.ccs/hosts.toml symlinks on each machine. A pre-existing real file or directory is reported as a conflict rather than overwritten. Thirty locations are curated today.

The boundary that matters: a path that exists on the laptop is never assumed to exist, or to be current, on the Mac Mini. The match payload reports the current host's validated path and Git facts. A selected remote target then validates its own canonical location during bounded SSH preflight. The Mini is preferred whenever eligibility, capabilities, and task-local-state checks pass; the laptop is the explicit exception for local-only state or after a pre-workspace remote failure that the user chooses not to pursue.

# ~/.ccs/config.toml
[routing]
registry = "~/Documents/milad-vault/ClaudeConfig/session-routing/locations.toml"
hosts = "~/Documents/milad-vault/ClaudeConfig/session-routing/hosts.toml"

# ClaudeConfig/session-routing/locations.toml
version = 1
default_host = "Milads-Mac-mini"
default_harness = "claude-gpt"
default_model = "gpt-5.6-sol"

[[location]]
key = "ccs"
name = "CCS"
aliases = ["claude sessions", "session catalogue", "session router"]
cwd = "~/Programming/Repos/claude-sessions"
kind = "repo"
eligible_hosts = ["Milads-M3-2", "Milads-Mac-mini"]
preferred_host = "Milads-Mac-mini"

Direct commands

The CLI exposes only deterministic primitives, which keeps a fast manual path when the destination is already known:

ccs start
# opens a fresh managed launcher with "/ccs:new " pre-filled and unsubmitted

ccs location list
ccs location show ccs
ccs location match --json "work on the session router"
ccs session new --top-level --location ccs --prompt "Implement issue 42"

Usage recency lives in CCS runtime state, not the registry file, to avoid Git churn. The registry README documents fields, precedence, registration, and retirement.

06 · Route

The exact model route

Harness and model come from the canonical routing policy through the birth compiler, never from raw model IDs written into prompt prose. The compiler matches the exhaustive current model set, including claude-opus-5, and emits exact launcher spellings. Precedence, highest first:

  1. Role policy
  2. Explicit model named in the request
  3. Explicit legacy launcher
  4. Location override from the registry entry
  5. Registry-wide exact default
  6. Legacy plain Claude, only outside /ccs:new

An invalid lower-priority default no longer blocks a valid explicit route. The optional warm Dock launcher runs Terra at medium effort, but the skill works from whatever model is currently running it. Its executable spelling is gpt-5.6-terra[1m]: gpt-5.6-terra is the canonical model ID, while [1m] is the gateway launch suffix for the one-million-token context variant, not an effort setting.

07 · Remote

Remote launch, and where it stays uncertain

The first-version remote transport is a cmux ssh workspace with a Mini-side inline birth:

cmux ssh macmini \
  --name "<title> [ccs:new:mini]" \
  --command '<remote ccs> session new --top-level --inline --cwd ... --prompt ...' \
  --no-focus

The remote executable, PATH, environment, and shell quoting are rendered by CCS from machine capability data, not assembled in plugin prose. One bounded preflight uses ConnectTimeout=5 and BatchMode=yes, then verifies remote CCS, readable location and host registries, canonical host identity, the selected location, the exact model, and every required capability before a workspace is created. The target command receives the same canonical model and capability requirements and validates them again.

{
  "status": "workspace_created",
  "session_id": "pending",
  "host": "Milads-Mac-mini",
  "location": "ccs",
  "workspace_ref": "workspace:501",
  "uncertainty": "Remote workspace creation succeeded, but session reservation and prompt delivery are not yet receipt-confirmed. Inspect this workspace before any retry."
}

Honest uncertainty

A local status: launched receipt proves UUID reservation, birth metadata, and successful workspace creation with the complete launcher command. It does not claim that the child process later consumed the prompt. Remote evidence is weaker: once any workspace reference exists, the session ID remains pending until target-side reservation is receipt-confirmed, and automatic retry or local fallback is forbidden. Agentic OS issue 34 defines a first-class Mini-native transport that can strengthen that receipt without changing the conversational router.

08 · Safety

Registration safety

No registry entry is ever created from an inferred name. Manual registration remains an explicit deterministic command; the conversational router registers an unregistered path only after a structured local status: launched receipt. Linked Git worktrees, .claude/worktrees, .worktrees, and operating-system temporary roots are mechanically rejected.

A registry update resolves and preserves the managed symlink target, preserves the destination file mode, writes a sibling temporary file, then atomically renames it over the destination. Register and retire operations touch only the targeted location table so existing comments and ordering survive.

Prompt transport is shell-isolated through UUID-scoped protected files, so quotes, backticks, command substitution, and shell operators stay literal prompt data. Malformed value-taking flags fail before the session is reserved rather than silently dropping a constraint.

09 · Rollout

Rollout order

Deployment follows a fixed sequence so that no launch runs against stale code, links, or host labels:

  1. Commit and push the reviewed CCS, vault, and Dock-seed revisions separately; re-pin both machine manifests to those exact revisions.
  2. Run the machine adapter on the laptop and Mini, verify the two managed runtime registry links, then install or reload the plugin.
  3. Run an immediate full CCS reindex on both machines. The host-label change must rewrite existing hostname-style catalogue labels to the canonical scutil names before source-host checks continue.
  4. Verify ccs start creates a fresh launcher with exactly one unsubmitted /ccs:new composer prefill. Then run one harmless local /ccs:new smoke and one Mini smoke. An uncertain Mini receipt is inspected, never retried automatically.
  5. Merge the staged Dock seed without replacing unrelated controls, activate it, and verify the Terra role launcher.

The Dock stays staged-only until the smoke launches pass. “Reviewed deployment proves parity” means the installed reviewed revisions pass the reindex, ccs start composer-prefill check, local and Mini launch smokes, direct-CWD and location routes, role-launcher check, and Dock gate. Only then may ClaudeConfig/claudes move to the vault archive. ccs start remains permanently as the thin interactive entry point; it does not regain routing logic.

11 · Open concern

The one item still open

A single Low-severity concern remains: the interim transport extracts workspace:<token> from unstructured cmux output. If cmux ever echoes a prompt-derived string in that shape, the receipt could record the wrong reference. The failure direction is safe: a false reference suppresses fallback and forces inspection; it cannot authorize an automatic retry.

12 · Boundaries

Constraints and non-goals

  • No unmanaged nested claude, claude-native, or claude-gpt process. Every persistent Claude Code process uses a CCS-managed birth.
  • No silent automatic retry after a CCS birth.
  • No hard-coded raw model IDs in prompt prose; the registry defaults and canonical compiler own route spellings.
  • No use of ClaudeConfig/claudes as a fallback route source once the registry ships.
  • No automatic registration from an inferred name; new entries require a validated path and an explicit selection.
  • No assumption that a path exists or is current on both machines without validation.
  • No remote placement for work that needs the laptop's local GUI, unsynced files, attached hardware, or a checkout not present and ready on the Mini.
  • No session-ownership transfer or cross-host transcript claiming here; that remains issue 34.
  • No resume under a command named new. Duplicate detection may warn, but the path always births a fresh session.
  • No second router in ccs start or skill prose. ccs start only creates the managed launcher and pre-fills the skill command; route policy, validation, and launch mechanics stay in typed CCS code.
  • The skill is explicitly user-invoked (disable-model-invocation: true) and does not auto-trigger on ordinary session discussion.
