Destroying a session, and never recording one

Two independent capabilities for ccs: a command that erases a session from the machine, and a session mode that keeps one out of every surface ccs writes. Today the tool has neither. archive and complete are flags that explicitly leave the transcript alone, and nothing in the entire command registry deletes anything.

01What is being built

These are two separate features that share a motivation. They are not layered on each other, and either could ship without the other.

ccs session destroy

Erases a session and everything below it in the causal tree (transcripts, index rows, catalogue rows, sidecar logs, task state, edit history) after closing any live processes involved.

Works on any session. Irreversible by design.

incognito sessions

A session marked incognito is excluded from every listing and aggregate, and, more importantly, from the background machinery that would otherwise ship its transcript to a model provider or splice it into another session's prompt.

Nothing lists them. Nothing deletes them.

The connection between them is narrow and deliberate: because nothing lists an incognito session, ccs session destroy . from inside the running session is the practical way to end one. That is a workflow, not a coupling. No code path in incognito calls destroy.

02What was decided, and what lost

Nine decisions came out of scoping. Eight had a live alternative that was rejected for a stated reason, and in most of those the rejected option was the more obvious choice until a specific fact killed it. The exception (D7, what incognito suppresses) was not a choice between options but a question of how far the suppression should extend, and the answer was: all of it.

Relationship between the two features

Independent. Incognito does not auto-destroy.

Browser incognito discards history on close, and copying that would have been the tidier story. It was rejected on a mechanical ground: the only places to hang auto-destruction are the Stop hook and the workspace-close path, and neither fires on a crash, a kill -9, or a reboot. A privacy feature whose guarantee silently fails open, leaving precisely the transcript the user believed was gone, is worse than one that never promised.

Rejected: auto-destroy on close; auto-destroy plus a reaper sweep to catch crashes. The reaper closes the hole but introduces a background process that deletes real transcripts unattended.

Blast radius of destroy

Recursive. The entire parent_session_id subtree dies.

The two descendant kinds are structurally unlike each other. Native subagents are stored inside the parent's own directory at ~/.claude/projects/<slug>/<parent-id>/subagents/agent-*.jsonl and quote the parent's task prompts verbatim, so leaving them would defeat the command outright. Delegated children (ccs delegate, ccs session new --child-of) are independent top-level sessions with their own workspaces. Recursion takes both.

Rejected: destroying subagents but orphaning delegated children with a nulled parent pointer. Gentler on a child someone is actively driving, but it leaves that child's transcript, which quotes the parent's instructions, intact, and its spend attributed to a session id that no longer exists.

Live sessions in the tree

Close every live workspace first, then delete. Abort if any close fails.

Half of this is forced by mechanics: a running claude process owns its JSONL and re-flushes it each turn, so deleting the file underneath it produces a resurrected transcript. The actual decision was the failure posture. Aborting the whole command when a close fails, before deleting anything, is what keeps "destroyed" from quietly meaning "partially destroyed." ccs already owns the verified close path (src/cmux/close-current.ts does stable-UUID workspace verification, src/cmux/reap.ts:220 closes by surface id), so this is wiring rather than new machinery.

Rejected: refusing outright when anything is live, which turns the common case (destroy the session I am sitting in) into a chore; and best-effort closing, which risks the exact resurrection the feature exists to prevent.

Confirmation

Preflight by default; execute only when the id is typed twice.

ccs session destroy <id> prints the full manifest and changes nothing. ccs session destroy <id> --confirm <id> executes, and the two ids must match. A preflight, throughout this plan, means a bare invocation that reports what would happen and mutates nothing, which is the convention every destructive-ish verb in ccs already follows. This gives the tool's only irreversible verb a stronger gate than the single --do flag that currently guards closing a duplicate workspace, while staying non-interactive so unattended callers do not hang.

Rejected: a TTY prompt that asks the operator to type the id, and plain --do (one fat-fingered flag away from an unrecoverable mistake). The TTY option was rejected because a prompt makes the command unreachable to every agent, hook, and future sweep, not because it would be unprecedented.

Correction, after the decision was taken. This decision was put to Milad with the supporting claim that ccs has no interactive prompt anywhere in its codebase. That claim was wrong. ccs triage runs a full readline question loop over stdin (src/enrich/triage-command.ts:115-117), so an operator-facing prompt would in fact have precedent. The other half of the rationale survives unchanged: a prompt would still make destroy unusable from automation. Flagged in chat for Milad to re-decide rather than silently kept.

Identities

Never touched. Reported in the preflight instead.

An identity (cluster:role:work-ref) is durable by design. The glossary is explicit that a session is a vessel and the identity outlives it, and core identities like control expect re-embodiment indefinitely. Deleting one because its last session died would destroy a longer-lived thing than the operator named. The cost of this choice is honest residue: ~/.ccs/clusters/<c>/identities/…/stop-context.md and inbox/processed/*.md hold session-authored prose that survives the destroy. The preflight names those paths so they can be cleared deliberately.

Rejected: cascading identity deletion once no session references it, which wipes core identities that are merely between embodiments; and a --with-identity opt-in, which adds another lever to the most dangerous command in the tool.

Residue in files ccs does not own

Erase everything ccs owns. Name everything that survives.

cmux writes ~/.cmuxterm/workstream.jsonl (currently 438 MB, append-only, held open by a live process) alongside a 14 MB events.jsonl. Rewriting another tool's live log to scrub lines risks corrupting it, and an APFS local snapshot is a read-only point-in-time copy, so the only way to remove a file from one is to delete the entire snapshot, which is far outside what this command should reach for. That makes the truthfulness of the command's report its single most important property: both the preflight and the completion output enumerate the surfaces that will still hold traces, so "destroyed" is never read as a guarantee the tool cannot make.

Rejected: line-scrubbing cmux and crash logs; purging ~/.ccs/backups/*.db snapshots, which exist to protect every other session from exactly this class of mistake.

What incognito suppresses

All four: enrichment and titling, cross-session context injection, cost aggregates, board and export.

The load-bearing fact is that enrichment is not a local operation. src/enrich/gateway.ts:202 POSTs the transcript tail to 127.0.0.1:8317, the claude-gpt proxy, which forwards to a model provider. So today every session's content leaves the machine automatically, via the launchd sweep and again via finish-current on close. Separately, resolvePredecessors (lineage.ts:79) and readSessionsSince (world.ts:174) compose prior-session content into a different session's prompt. Hiding a row in a list while still shipping its transcript offsite and splicing it sideways into unrelated sessions would make the label a lie.

Carrier, entry, and discoverability

A boolean column on catalogue; settable at birth and mid-session; nothing lists them.

Tags were the obvious carrier and are the wrong one. session_tags has zero readers in any listing path (not ccs ls, not the Go TUI, not catalogue export), so implementing incognito as a tag would mean adding a brand new join at all sixteen sites enumerated in the next section. The two attributes that already hide sessions (archived, and the auxiliary session class used for subagent-shaped bodies) work because they are columns on catalogue, which is why a single expression at cli.ts:526 and load.go:136 covers them. In addition, session_class feeds the pre-computed catalogue_hidden_sessions table that the whole cross-product protocol reads through a single predicate.

Both entry points ship. ccs session new --incognito is airtight: no window exists in which the session was ever enriched. ccs incognito . handles the session that turns sensitive halfway through, and additionally deletes any enrichment already stored, so a sweep that ran before the mark is undone locally.

Rejected: a third session_class value. It would conflate two orthogonal axes: a session can legitimately be both auxiliary and incognito, and one column cannot say both.

Slash commands

/ccs:incognito sets the mode. /ccs:destroy previews and then waits for a human.

The naming avoids a live collision. /ccs:archive already exists and already means "hide this session from active views without touching its transcript," so calling the new one /ccs:hide would give the much stronger operation the weaker word, and leave two near-synonymous commands where only one of them stops a transcript being shipped to a model provider.

The destroy flow is the more consequential half, because a slash command is typed by the agent, not the operator. Had /ccs:destroy run the preflight and then immediately re-invoked with --confirm, the double-id check would have protected nothing: the same process would supply both ids from one variable, and the entire gate would collapse into the act of emitting one command. So the command runs the bare preflight, prints the manifest, and stops. Execution requires an explicit go-ahead in the next message. The human confirmation moves into chat, where it can actually be read before an irreversible recursive delete, and the CLI gate keeps its meaning because a person authorized the second half of it.

Rejected: preview-and-execute in one shot, which scrolls the manifest past after the deletion and lets any loop that can emit the command destroy a subtree; and preview-only, which never lets an agent execute at all but adds a copy-paste step to every use.

03Where the filter has to reach

There is no single choke point. Of the sixteen places that would need to know about incognito, exactly two are shared filter chains that many surfaces read through. The other fourteen each re-derive the same predicate by hand, because the TypeScript side has no shared filter helper at all. This breadth, not any single hard problem, is the bulk of the incognito work.

Two traps in that bottom row deserve naming, because both fail silently. The Go TUI's buildStats (load.go:453) iterates the raw indexed rows rather than the filtered set, so spend leaks straight past includeSession() unless it is handled separately. And src/hooks/compose-predecessors.ts:27 feeds resolvePredecessors output into turn injection, the one path where an incognito session's content would surface inside a different session's context window rather than merely appearing in a list.

04What destroy actually deletes

There are zero foreign keys and zero cascades in catalogue.db: PRAGMA foreign_key_list comes back empty for every table. Every row in every table must be deleted explicitly, in a known order.

Correction: the category tables are owned

An earlier draft of this plan claimed session_category_assignments and its siblings had no CREATE TABLE anywhere in src/ and were therefore schema drift from an outside writer. That was wrong — it came from reading a stale local master. On origin/master they are created and owned by db-schema.ts, alongside every other catalogue table. There is no drift to resolve. Destroy still guards on table existence before deleting, because a store created by an older binary genuinely may not have them, and an unguarded DELETE would fail the whole transaction.

Order of operations

  1. Resolve the subtree by walking parent_session_id, and read index.sessions for each member's path and shadow_paths. That index row is the only record of where the transcript files are, so it must be read before anything is deleted.
  2. Print the manifest. Without --confirm, stop here.
  3. Close every live workspace in the tree through the verified close path and wait for exit. Any failure aborts before a single deletion.
  4. Delete transcripts: the primary path, every shadow path, and the subagents/ directory.
  5. Delete the Claude Code sidecars and the ccs per-session logs.
  6. Delete catalogue rows in one transaction, then index rows and FTS entries.
  7. Print what was destroyed, and what still holds traces.

05The risk this plan accepts

Incognito sessions accumulate invisibly, forever

Because nothing lists them and nothing deletes them, an incognito session closed without an explicit ccs session destroy . (a crash, a force-quit, or simply forgetting) persists on disk permanently with no ccs command able to surface it. Its transcript stays, its spend stays, and it becomes reachable only by reading ~/.claude/projects by hand and passing the id to destroy directly, which does still work.

Two ways out of this were offered and both were rejected. An ls --incognito flag would list them on request, mirroring how --all already reveals archived sessions, but it means one command exists that enumerates the private set, which defeats the point of the mode. A retention sweep would auto-destroy incognito sessions past some age, but that is unattended deletion of real transcripts on a timer, and a timer set wrong deletes work nobody asked it to.

06Shape of the work

The catalogue schema is at CATALOGUE_VERSION = 40 (src/catalogue/db-schema.ts), and v41 is already claimed by an in-flight enrichment branch that drops the enrichment_* columns. Stamping past it here would make that branch's v < 41 check false on a live store and silently skip a drop it believes it performed. So incognito lands off the version ladder, behind a hasColumn presence guard, following the enrichment_declined precedent already in the same file. CATALOGUE_VERSION stays at 40 and the two branches do not collide.

The version-gated blocks keep their existing discipline either way: migrate() opens BEGIN IMMEDIATE, applies each block, then runs validateSchemaPostcondition before COMMIT, so a migration that produces a malformed schema rolls back both the DDL and the version stamp together.

Verification

Beyond bun test and tsc --noEmit, three properties are worth pinning with tests, because each one fails silently if it regresses:

  • Destroy against a fixture store ($CCS_ROOT plus a temp Claude home) leaves no file or row mentioning the session id, across every surface in the table above.
  • An abort, triggered by a close that fails, deletes nothing at all.
  • An incognito session never appears in enrichCandidates, resolvePredecessors, or readSessionsSince. This is the property that makes the label honest, and the one most likely to rot quietly.

Work happens on feat/session-destroy-and-incognito in an isolated worktree off fresh origin/master. Because ccs is fleet infrastructure and this adds its first irreversible command, the branch will be committed and pushed but held for review rather than self-merged.

07What actually shipped

Built on feat/session-destroy-and-incognito, 2026-08-09. Two ADRs record the decisions: ADR-0097 (incognito) and ADR-0098 (destroy).

Where the build diverged from the plan

  • The schema change is off the version ladder. The plan said v41; v41 turned out to be reserved by an in-flight enrichment branch, so the column landed presence-guarded with CATALOGUE_VERSION unchanged at 40. Section 06 above is corrected.
  • Four filter sites were missed by the original scope pass. sidebar/{catalogue-read,snapshot}.ts, categories/analytics.ts, doctor/session-integrity.ts, and the live-sibling warning in resume/resume-session.ts all name or print session ids and were added.
  • Two aggregate counters leaked what the row filters hid. The ccs ls footer computes rows.length - shown and reports it as "N hidden … --all to show" — which would have announced an incognito session's existence while pointing at a flag that does not reveal it. The Go dashboard's buildStats sums Spend over raw index rows, bypassing includeSession entirely, so an incognito session moved the visible total. Both are fixed by removing incognito rows from the input rather than skipping them at render time.
  • Incognito costs birth-integrity auditing. Every finding ccs doctor sessions emits carries the session id, project, and title, so a marked session had to leave that report entirely rather than merely pass its checks.
  • The sidebar cannot filter when the catalogue is unreadable. The catalogue is the only record of which sessions are marked. This degrades identically to the existing auxiliary exclusion, and is a broken-machine state rather than a routine one.

Risks the plan flagged, and how they turned out

  • Real. The plan's concern that a mid-session mark is inherently late holds: the enrichment sweep may already have POSTed a transcript tail. markIncognito clears the stored row, which is the only half still undoable locally. The CLI and the /ccs:incognito command both say so out loud, and --incognito at birth is presented as the airtight path.
  • Real, and it is why the ordering is what it is. A live claude re-flushes its transcript each turn, so the close-first ordering is load-bearing rather than defensive. It is pinned by a test that fails a close and asserts every path still exists.
  • Unresolved by design. Backups are per-store, not per-session, so recovering from a mis-aimed destroy means restoring a whole catalogue or nothing. The two-step confirm and the manifest are the mitigation; there is no undo.

Verification

tsc --noEmit (both projects) clean, go build ./... and go test ./... clean, and eight new tests in src/catalogue/{destroy,incognito}.test.ts pin the three properties named above. The CLI was exercised end to end against a scratch $CCS_ROOT: manifest, confirm mismatch, incognito mark, ccs ls with and without --all, and the destroy itself.
