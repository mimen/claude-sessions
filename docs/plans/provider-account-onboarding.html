02 What "an account" actually is here

There is no account registry. An account is a tuple of state in four independent places.

Nothing in the vault, in models.toml, or in 1Password knows what accounts exist. Account state is entirely local and per-machine, and the four layers below do not know about each other. This is the single most important thing to understand before adding one, because forgetting a layer produces a partial account that works for traffic but is invisible to reporting, or vice versa.

The critical asymmetry the diagram shows: the gateway credential is what serves traffic, CodexBar is what reports usage, and they are separate OAuth grants on the same ChatGPT account. Logging in once does not do both. The existing Claude setup has exactly this same two-logins-per-account property, recorded in the gateway runbook: a dead Claude account needs both cswap add and cliproxyapi -claude-login.

gateway credential
One JSON file per credential in ~/.cli-proxy-api/. The gateway loads every *.json there. Codex files carry access_token, refresh_token, id_token, email, account_id, type: "codex", disabled. Note they carry no priority key today, unlike the Claude files.
~/.codex/auth.json
The Codex CLI's own login. Single-slot. Nothing in ClaudeConfig/bin/ reads or writes it; the gateway explicitly does not touch it.
CodexBar
The usage reader ccs usage shells out to. Registers accounts through its GUI into managed-codex-accounts.json — a file that does not exist yet on this machine.
1Password Sol
Holds nothing account-related. No ChatGPT, OpenAI, Codex, Anthropic, or Claude login item exists among the vault's 103 items, and §09 argues it should stay that way.
models.toml
Has a provider field per model, but that names a lane, never an account. There is no account concept in the model registry, the slots table, or the launcher registry.

03 The gateway credential

One command. The gateway names the file, and the name encodes the plan tier.

This is the step that actually gives the fleet more capacity. Everything else in this document is reporting and ergonomics.

# signed in to the browser as milad@afternoonumbrellafriends.com
cliproxyapi -codex-device-login

# produces, alongside the existing Pro credential:
~/.cli-proxy-api/codex-<hex>-milad@afternoonumbrellafriends.com-plus.json

The filename is derived by the gateway from the https://api.openai.com/auth.chatgpt_plan_type claim in the id_token, which is why the existing credential ends -pro. Do not hand-name these files and do not copy them between machines. Refresh tokens rotate on use, so a copied credential invalidates the origin machine's grant.

There is direct precedent that the gateway holds two Codex credentials happily: the runbook records a second codex-…-prolite credential coexisting with the Pro one. The gateway's multi-credential handling is entirely provider-agnostic. What is Claude-only is the tooling around it, which is §07.

Set priority explicitly The existing Codex credential carries no priority key at all, so it defaults to 0. With routing.strategy: "fill-first", adding a second credential at the same implicit zero makes the drain order arbitrary. Whichever policy §04 settles on, set both Codex rows' priority explicitly rather than relying on defaults. 
PATCH http://127.0.0.1:8317/v0/management/auth-files/fields
{"name": "codex-<hex>-<email>-plus.json", "priority": 50, "disabled": false}

A detail worth noticing separately: the credential files in ~/.cli-proxy-api/ are mode 644, world-readable, while ~/.codex/auth.json is 600. That is the gateway's own default, it predates this work, and it is worth tightening on its own schedule rather than as part of this change.

04 The routing decision

The only genuinely blocking question, and it is about money rather than code.

The gateway supports two arrangements, and the existing Claude setup deliberately picks the stricter one. The question is whether Codex should copy it.

For Claude, the parked account is disabled, not merely de-prioritized. The runbook records why: failover is always on and cannot be turned off, so a dead or throttled target would silently start serving the other account. Disabling the parked credential makes account attribution deterministic. The budget-pools plan states the underlying principle plainly:

No total. Show both accounts and let the cascade order carry the meaning. Totalling a business entitlement into a personal figure invites spending it by accident.

That reasoning transfers directly, because milad@afternoonumbrellafriends.com is the AUF business identity. But it cuts against the reason for buying the account in the first place, which was relief when Codex runs dry — and it is dry right now. Automatic overflow is the feature; silent business spend is the same feature seen from the accounting side.

OptionMechanismWhen Pro is exhaustedCostVerdict
Overflow Both credentials enabled. Pro at higher priority, Plus below it. fill-first plus always-on failover does the rest. Work continues automatically on the Plus account. No human in the loop. Personal work silently spends AUF quota. No record of which account served a session (§10). Recommended
Mirror Claude Plus credential present but disabled: true. A deliberate act enables it and disables Pro. Work stops until switched by hand. No Codex equivalent of fleet-switch exists to automate it (§07). Clean billing separation, at the price of the outage the account was bought to prevent. rejected
Overflow plus alarm Overflow, plus a notification the first time the Plus account serves traffic in a window. Same as overflow, with the spend made visible as it starts. Needs a watcher that does not exist. Real scope, not a config flag. later

The recommendation is overflow, on the grounds that a $20 Plus allowance is small enough that accidental spend is bounded by roughly the cost of the plan, while the outage it prevents is unbounded. That argument depends on the premise that the amount at risk is small; if the AUF account is ever upgraded, this decision should be revisited rather than inherited.

A policy consequence worth pricing in fleet-autoswitch decides purely on usedPct. A percentage-based policy treats a $20 Plus account and a $200 Pro account as equally attractive at the same utilization. This does not bite today, because autoswitch is Claude-only (§07), but it is a trap for anyone who later extends it to Codex.

05 Usage visibility

One GUI registration, one argument, one registry row.

CodexBar has to learn the account first

CodexBar 0.60.2 supports multiple accounts per provider, through a Codex-specific mechanism distinct from the tokenAccounts array that API-key providers use. Its help text is explicit:

Use --all-accounts to fetch every token account, or every visible
Codex account for Codex.

Registration is a GUI action — Add Account… in the Codex section — with no config key to hand-edit. Its config file at ~/.config/codexbar/config.json is only an enable list of provider ids and carries no account data at all. Registering writes ~/Library/Application Support/CodexBar/managed-codex-accounts.json, which does not exist yet.

Understand this before clicking CodexBar's Codex model is a switcher over one system account, not N concurrent live sessions. Registering the second account rewrites ~/.codex/auth.json, the file the codex CLI itself reads. Its own error strings admit the hazard: "CodexBar could not safely preserve the current system account before switching." Expect the inactive account's numbers to come from a cached snapshot with an older updatedAt rather than live. This was not provable read-only and should be confirmed immediately after registering.

The one line of code

The adapter already loops over multiple entries and already suffixes entitlements with the account email — it was built for exactly this case, for Anthropic. It simply never asks CodexBar for more than one account:

// src/usage/adapters.ts:126 — today
const res = runCodexBar(providerArg);

// the receiving signature already accepts it, codexbar.ts:54
export function runCodexBar(provider: string, extraArgs: readonly string[] = [])

// the fix, for the codex call site
const res = runCodexBar(providerArg, ["--all-accounts"]);

The comment sitting directly above accountEntitlement() in that same file describes the Anthropic precedent that makes this work, and the entitlement grammar is <base>:<email>#<product>. A second Codex account therefore emits codex-pro:milad@afternoonumbrellafriends.com with no further change.

One registry row

Without it the group renders live meters but no plan name and no renewal date. src/usage/subscriptions.ts already holds a row per account for Anthropic:

{ provider: "codex", account: "milad@afternoonumbrellafriends.com",
  planName: "Codex Plus", monthlyDollars: 20, anchor: "<YYYY-MM-DD>" },

One cosmetic defect to fix or accept

adapters.ts:188 hardcodes the entitlement base as the literal string "codex-pro". A Plus account will therefore carry the id codex-pro:milad@afternoonumbrellafriends.com in --json. The displayed plan name comes from the registry row above, so the terminal reads correctly and only the JSON contract lies. Low severity, but it should be recorded before anything downstream is built on that field. The Anthropic path does this better and carries a real tier field.

06 Menubar and hub need nothing

The surfaces downstream of ccs usage are already account-keyed.

This is the pleasant part. CcsUsage.app (/Applications/CcsUsage.app, running as the resident LaunchAgent com.milad.ccs.usage-menubar, polling every 5 minutes) shells ccs usage --json and renders one gauge group per entitlement. It needs no change and no rebuild — a new entitlement appears on its own. Its binary already carries the string codex|personal alongside anthropic|personal and anthropic|auf.

Better still, the display name is already correct without configuration. The alias map in src/usage/render.ts is keyed by bare email rather than by provider:

const aliases = {
  "miladmaaan@gmail.com": "personal",
  "milad@afternoonumbrellafriends.com": "AUF",
};

So the new account renders as Codex · AUF, sorted into the existing Codex block, with no edit. cswap-fleet-report likewise forwards the usage snapshot verbatim to the hub — it has a self-check asserting body["usage"] == snapshot — so the hub picks the account up for free.

Three surfaces investigated turned out to be irrelevant and should not absorb any effort. x-sub-watch is an X/Twitter timeline watcher, not a subscription watcher, and has one scaffold commit. provider-marks.ts and brand-icons.ts are unreferenced dead code with zero call sites. SwiftBar is installed but has never been configured. Also worth correcting: claude-swap-menubar-prototype is not a prototype — it is the live source of cswap v0.27.0b1, a fork of realiti4/claude-swap, and its installed version matches its pyproject.toml exactly.

07 Account switching stays Claude-only

Not an oversight to patch in passing. It is enforced by code, with a test pinning it.

You asked for account switching. It is worth being direct: for ChatGPT it does not exist, and this plan deliberately does not build it. Every layer of the switching stack filters to Anthropic by explicit code.

cswap-cliproxy-sync._classification() keeps only gateway rows whose provider or type casefolds to "claude". Codex, xai, and OpenAI-compatible rows are dropped before any priority write. cswap-fleet-report.gateway_states() applies the same filter and has a self-check asserting a codex row yields an empty dict — that behaviour is pinned on purpose. Above them, cswap itself is a Claude Code credential manager backed by the macOS keychain, and fleet-switch, fleet-reconcile, and fleet-autoswitch all drive cswap switch, so the entire fleet layer is Claude-only by construction.

For completeness, the Claude switch is genuinely involved. fleet-switch writes a desired state to the hub — aborting the whole run if that write fails, so a sleeping Mac converges later rather than being stranded — then for each shared-vault host runs cswap switch, which fires a postSwitch hook that reprioritizes gateway credentials through three ordered PATCH calls. It enables the target first, so a mid-flight failure never leaves every credential disabled, then verifies the resulting state and retries up to three times against an 8-second deadline.

Reproducing that for Codex is a real project, and §04's overflow recommendation is partly an argument that it is unnecessary. Overflow gets the benefit of switching without building switching, because fill-first plus always-on failover already moves traffic between credentials. If §04 instead settles on mirroring Claude, this section becomes required scope and the estimate changes substantially.

08 Per-machine reality

Account state does not sync. The vault carries none of it.

The shared vault propagates scripts and the model registry, but every layer in §02 is local to one Mac. The Mini needs its own cliproxyapi -codex-device-login and its own CodexBar registration, and neither can be satisfied by copying files, because refresh tokens rotate on use.

This matters more than it first appears, because the Mini runs fleet-report and fleet-reconcile on timers and is the leader for fleet-autoswitch. A half-provisioned fleet — the new account on the laptop only — means the laptop overflows to Plus while the Mini still hard-fails at the Pro limit. Either provision both or accept that asymmetry knowingly.

09 The playbook

Where it lives, what shape it takes, and the judgments it has to encode.

You asked for a reusable playbook for adding accounts. The natural home is ClaudeConfig/modes/infra/playbooks/provider-account-lifecycle.md, beside model-lifecycle.md, which is the closest existing analogue and the right formal model to copy. That playbook opens by naming what the agent owns and what evidence proves it — "You own one registry edit and the proof that every consumer followed it" — then runs numbered steps each ending in a verifiable state, and closes with a required reply shape.

The account playbook's equivalent framing: you own one credential per layer and the proof that usage reporting sees it. Its completion evidence is ccs usage printing the new account as its own group with a correct plan name, and the gateway's auth-files endpoint showing the intended priority.

Steps the playbook must cover

  1. Decide the routing posture before touching anything. Overflow, or parked-and-disabled, and why. This is the §04 decision and it recurs for every future account.
  2. Gateway login. The provider's own device-login command. Never hand-name, never copy between machines.
  3. Set priority explicitly through the management API. Do not inherit defaults.
  4. Register with the usage reader — CodexBar GUI for OAuth providers, tokenAccounts config for API-key providers. Note the hazard that registration may rewrite the live system account.
  5. Add the subscription registry row in src/usage/subscriptions.ts, in the deployment checkout.
  6. Add a display alias in render.ts if the email is new to the fleet.
  7. Repeat on every shared-vault host from hosts.toml. State plainly that nothing syncs.
  8. Verify with ccs usage, ccs usage doctor, and a real dispatch to a model on the new lane.
  9. Update routing policy separately, if at all — mirroring model-lifecycle's step 7, which insists policy edits happen after availability is proven, never as part of provisioning.

Two judgments the playbook should encode as rules rather than leave to each run. First, credentials do not go in 1Password. No provider login item exists in Sol today, and a rotating OAuth pair would go stale on first refresh — the everyday service account is read-only by design, so it could not write the new value back anyway. The house pattern is that a dedicated local tool owns the credential and CCS consumes its JSON: cswap owns the Claude keychain, CodexBar owns the Codex snapshot store. Second, reporting layers and traffic layers are separate logins, and a checklist that does only one produces an account that works but is invisible, or is visible but serves nothing.
