Verdict: ccs has no resume defect here, and --worktree should not be implemented.

claude --resume <id> finds a session by looking in the project folder for the current directory, and — on a miss — searching the project folders of every git worktree of the repo the current directory belongs to. Nothing consults a session→worktree binding. --worktree plays no part in finding a session.

The transcript lives under -Users-mimen-Programming-Repos. From /Users/mimen/Programming/Repos it is found on the first lookup — which is exactly the command ccs already builds. From inside the worktree it is unreachable, because the parent directory of a repo is not one of that repo's worktrees. The variable was cwd, and ccs had the cwd right.

Everything below is read out of the shipped binary, not inferred. Earlier revisions of this document argued the opposite on weaker evidence; §7 records what was wrong and why.

0.4 Battle-test verdict (final)

cmux is faithful; ccs computes the right dir; the real bug is stranded storage folders.

  • 9 live instrumented spawns, 0 cwd mismatches — including spawns that correctly landed inside a live git worktree. The "cmux ignores --cwd" theory (§0.2) is dead. cmux launches exactly where ccs asks.
  • Sweep of all 1,954 non-subagent sessions: 1,266 resume fine; 688 do not, and they collapse to 10 directories / 2 causes — 593 whose cwd became a symlink (the imsg convex-db migration: imsg, imsg/client, t3code-spike-sessions) and 95 whose dir was deleted (dead worktrees, temp scratch).
  • Live-confirmed the symlink strand: claude --resume <imsg-id> from the symlinked ~/Programming/Repos/imsg → "No conversation found," because the harness encodes realpath(cwd) and the physical folder ≠ the transcript's logical folder.
  • ccs already detects both (the "could not confirm storage dir" / "original cwd is gone" notes) but then spawns a doomed workspace instead of failing clearly. That — detection quality — is the one real improvement the whole investigation surfaced. Recovery recipes for both classes are verified and in ADR-0092.

Cleanup done: instrumenting cmux shim deleted; ~/.ccs/spawn-cwd-probe.log kept as evidence (9 spawns, 0 mismatches). The empty convex-db/.claude/worktrees/imsg-priority-shelf dir was recreated to recover bd0948c0 and left in place for that resume.

0.2 SECOND reopening — the actual incident was never diagnosed

Milad's account: he resumed via the ccs TUI (Enter); ccs opened a fresh workspace, a new shell, and typed the resume command itself; that shell was in the worktree, the typed resume failed, and a manual cd to the repo fixed it.

This is the spawn path, and it defeats every "ccs is fine" conclusion below:

  • focusSession (src/cmux/liveness.ts:77) only runs select-workspace + focus-window — it never types a command. So this was not the already-open focus path.
  • The spawn path calls resolveResumeCwd, which for this session provably returns /Users/mimen/Programming/Repos — one index row, one transcript; both the early-return and the fallback walk resolve to the repo, and the worktree encodes to a different folder name so the walk cannot return it.
  • spawnCmux (src/resume/spawn-cmux.ts:38) passes that cwd explicitly: cmux new-workspace --cwd /Users/mimen/Programming/Repos ….
  • Yet the shell was in the worktree.

All four facts hold at once, so the wrong cwd did not come from ccs's computation. The remaining explanation — consistent with the worktree having a live, persisted cmux workspace at 14:44 — is that cmux new-workspace did not honour --cwd, reusing the session's persisted worktree-cwd workspace instead. ccs handed cmux the right directory; cmux launched elsewhere. A distinct defect at the ccs→cmux boundary, adjacent to ADR-0021 Issue 2 (cmux faithfully restores a drifted cwd), and NOT what ADR-0092 documents.

Confidence: the only explanation consistent with all four verified facts, but it rests on an unconfirmed cmux behaviour and the 14:44 state is gone (the successful manual resume, pid 71735, is now live at the repo). Hence: instrument before any fix or ADR rewrite.

0.3 Instrumentation — an out-of-repo cmux shim

An in-repo probe (edit to spawn-cmux.ts) was landed and then wiped within minutes by concurrent development on the claude-sessions checkout — the same reset also reverted the locate.ts comment from ADR-0092. Uncommitted source edits are not durable in this tree right now, so the probe was moved outside the repo entirely.

~/.ccs/cmux-probe-shim.sh wraps cmux. Because spawnCmux resolves opts.cmuxBin ?? process.env.CMUX_BIN ?? "cmux" (spawn-cmux.ts:35), launching the TUI as CMUX_BIN=~/.ccs/cmux-probe-shim.sh ccs routes every cmux new-workspace ccs issues through the shim. For new-workspace it records the --cwd ccs requested vs the workspace's actual current_directory (from cmux list-workspaces --json), appending a JSON line with a mismatch flag to ~/.ccs/spawn-cwd-probe.log; every other subcommand passes through untouched. 1. How --resume <id> actually resolves a session

The lookup chain, from the resume entry point:

else if (typeof e === "string") n = await C8e(e) ?? await Ng_(e), s = e;
C8e(id) — the direct hit
Loads <projectDirFor(cwd)>/<id>.jsonl, where the project dir is hz(p) = join(projectsRoot, encode(p)) — the same non-alphanumeric → - encoding ccs/src/resume/locate.ts:25 already mirrors.
Ng_(id) — the fallback, and the whole story
async function Ng_(e) {
  for (let t of await lRe(sn()))                        // lRe(cwd) = `git worktree list --porcelain`
    for (let r of await qL(t)) {                        // qL(path) = project dir(s) for that path
      let n = await C8e(e, join(r, `${e}.jsonl`));
      if (n) return M("tengu_resume_worktree_fallback", {}), n
    }
  return null
}
  • sn() → the process's original cwd.
  • lRe(dir) → shells out to git worktree list --porcelain in dir, returning that repo's worktree paths (current one first). Not a repo ⇒ empty list.
  • qL(path) → the ~/.claude/projects/ folder(s) for a path, including long-path truncation siblings.

Its own telemetry name says what it is: tengu_resume_worktree_fallback. The search is scoped to sibling worktrees of the current repo — it is not global, and it never walks upward to a parent directory.

2. What the "Resume this session with: --worktree" line actually is

It is an exit-time hint, emitted from the graceful-shutdown path:

function r$s() {
  if (JOo) return;                                   // print at most once per process
  if (process.stdout.isTTY && q1() && !ere()) try {
    let e = wt();                                    // THIS process's session id
    if (!Isn(e)) return;
    let n = Gbc(), o = n ? `--worktree ${n} ` : "";  // THIS process's worktree
    writeSync(1, dim(`\nResume this session with:\nclaude ${o}--resume ${r}\n`)), JOo = true
  } catch {}
}
function Gbc() { if (dUr) return dUr.enteredExisting ? null : dUr.worktreeName; return z1i }

Three consequences, each of which contradicts how I read that line originally:

  1. It is not a refusal. It is printed on the way out, telling you how to come back. It also fires on the failure path, because that path exits via the same graceful shutdown (mu(1)) — which is why a failed resume can print it.
  2. The worktree name describes the process, not the session. Gbc() reads process-local state about a worktree this process created. It performs no session→worktree lookup. Running from inside a worktree is sufficient to make that flag appear.
  3. ~/.claude.json is not involved. No activeWorktreeSession read anywhere in this path.

So --worktree is a flag for where you want to work, not for which session to find. Implementing it in ccs would add a token that cannot affect whether a session is located.

3. Does ccs have a defect?

3.1 The resume path — no

resolveResumeCwd returns a directory D only when encode(realpath(D)) === storageFolder (src/resume/command.ts:65, and the locate.ts walk enforces the same predicate). That is precisely C8e's requirement, so any directory ccs returns produces a first-lookup hit — it never even needs the worktree fallback. Measured on the trigger session: 

parsed cwd      : /Users/mimen/Programming/Repos
resolveResumeCwd: { cwd: "/Users/mimen/Programming/Repos", note: null }
argv            : claude --resume 3b292f6d-6756-4bbc-bba7-e12e09a1f53f

That is the command that worked. note: null was correct; there was nothing to warn about.

ccs's storage-folder-first design is in fact stronger than the harness's own fallback: Ng_ can only find sessions inside sibling worktrees of the current repo, whereas locate.ts decodes the storage folder to its real directory from anywhere. The README's premise — that the harness's own resume UX is directory-scoped — survives this investigation intact.

3.2 parse.ts:137 / :138 — a metadata defect, unrelated to resume

cwd and gitBranch are first-wins and ignore all 429 relocated records, so a session that moved shows its birth values. For the trigger session branch is "HEAD" rather than worktree-ccs-delegated-sessions. This cannot corrupt a launch dir (§3.1) but it does affect display and the git/PR sensing in catalogue/db.ts. Fixing it requires schema v9 + a forced reparse of 4,702 transcripts (see §5) — a poor trade for cosmetics. Recommend leaving it, with a comment recording why.

3.3 The one genuinely broken session

754b9a1a (imsg): its transcript sits in a worktree project folder whose directory has been deleted. The locate.ts walk finds nothing, so ccs falls back to the recorded birth cwd — which does not encode to the storage folder, so the emitted command will fail. ccs does emit a note. This is a dead-worktree problem, not a --worktree problem, and it is unfixable from ccs's side: the directory that would satisfy C8e no longer exists.

5. Why a "small" metadata fix is not small

Preserved from the pipeline survey, since it governs any future transcript-derived column:

reindexStore skips re-parsing when a transcript's mtime + size + path are unchanged (src/index/index.ts:177-184). Every session of interest here is closed, so a new content-derived column stays NULL forever on exactly the rows it was added for. Populating it means deliberately taking the drop-and-rebuild branch of the v8→v9 migration (src/index/schema.ts:32-44) rather than the additive ALTER — a full reparse of 4,702 transcripts including a 46 MB file. Rows are declared rebuildable cache (schema.ts:3), so this is legitimate; it is simply not worth spending on §3.2.

6. Recommendation

  1. Write no worktree code. §1 and §2 remove the motivation entirely.
  2. Record the finding. An ADR (next free number 0091 — 0090 is taken twice) documenting: the harness's resume lookup is cwd project dir → sibling-worktree project dirs; the --worktree exit hint is cosmetic and describes the process, not the session; ccs deliberately ignores it. Direct precedent: ADR-0021, already about Claude Code resume-cwd drift. This is the durable value of the whole investigation — it stops the next person re-deriving it from a misleading hint.
  3. Optionally, extend locate.ts's header comment with the Ng_ fallback, so the storage-folder rule is documented as necessary and sufficient.
  4. Leave §3.3 alone — unfixable — and §3.2 alone unless a schema bump is happening for another reason.

7. Open question

What did ccs actually show you?
The claim that started this — "the cwd was wrong in CCS, it was trying to resume from a different location" — is not reproducible. Running ccs's real functions against this session yields /Users/mimen/Programming/Repos, the directory that works. ccs resume-session <id> --dry-run currently answers "already open — nothing to do", so it may never have computed a directory at all. Candidates: a cmux workspace opened earlier in the worktree and reused; the TUI's displayed cwd (which is stale, per §3.2) mistaken for the launch dir; or a different session id. Until this is pinned down, there is no evidence of a ccs bug — and if the answer is "the TUI cwd column", then §3.2 is the whole complaint and the fix is cosmetic.
